2. **H5 适配：** 在移动端 H5 开发中，如何解决不同屏幕尺寸的适配问题？（如 rem、vw/vh、px to viewport 等）。

   在移动端 H5 开发中，适配的目标是：**在不同尺寸的手机屏幕上，页面元素能按设计稿的比例等比缩放**。

   以下是目前主流的 3 种适配方案及其原理：

   ---

   **1. Viewport 视口设置（适配的基石）**

   无论使用哪种方案，必须在 HTML 的 `<head>` 中加入这行代码，防止浏览器默认缩放：

   ```html
   <meta name="viewport" content="width=device-width, initial-scale=1.0, maximum-scale=1.0, user-scalable=no">
   ```
   *   `width=device-width`: 让视口宽度等于设备物理宽度。
   *   `initial-scale=1.0`: 初始缩放比例为 1。

   ---

   **2. rem 适配方案（经典方案，兼容性好）**

   **原理：** `rem` 是相对于根元素 `<html>` 的字体大小（font-size）的单位。通过 JS 动态修改根元素的 `font-size`，从而改变所有使用 `rem` 单位的元素大小。

   **实现步骤：**
   1.  **动态计算根字号：** 假设设计稿宽度是 750px。
       
       ```javascript
       function setRem() {
           const scale = document.documentElement.clientWidth / 750;
           // 假设 1rem = 100px (在 750px 设计稿下)
           document.documentElement.style.fontSize = (100 * scale) + 'px';
       }
       window.onresize = setRem;
       setRem();
       ```
   2.  **代码编写：** 如果设计稿上一个按钮是 `150px`，则代码写 `1.5rem`。

   **工具推荐：** `lib-flexible`（阿里早期方案）或手写简单的 JS 计算。

   ---

   **3. vw/vh 适配方案（现代主流方案）**

   **原理：** `vw` 是视口宽度的百分比（1vw = 视口宽度的 1%）。它不需要 JS，纯 CSS 实现。

   **实现逻辑：**
   *   如果设计稿宽是 750px，那么 `750px = 100vw`。
   *   `1px = (100 / 750) vw`。
   *   如果一个元素在设计稿上是 `150px`，代码里写：`150 * (100 / 750) = 20vw`。

   **优点：**
   *   **纯 CSS：** 不依赖 JS 脚本，性能更好。
   *   **语义清晰：** 直观对应视口比例。

   ---

   **4. 自动化转换：px to Viewport / rem**

   手动计算 `rem` 或 `vw` 非常痛苦。在实际项目（如 Vue/React）中，我们通常直接写 `px`，然后通过 **PostCSS 插件**在编译阶段自动转换。

   **A. 转换 px 为 vw（推荐）**

   安装 `postcss-px-to-viewport` 插件：
   ```javascript
   // postcss.config.js 配置
   module.exports = {
     plugins: {
       'postcss-px-to-viewport': {
         viewportWidth: 750, // 设计稿宽度
         unitPrecision: 3,    // 转换后的精度
         viewportUnit: 'vw',  // 转换成的单位
         selectorBlackList: ['.ignore'], // 不转换的类名
         minPixelValue: 1,    // 小于 1px 不转换
       }
     }
   }
   ```

   **B. 转换 px 为 rem**

   安装 `postcss-pxtorem` 插件：
   ```javascript
   // postcss.config.js 配置
   module.exports = {
     plugins: {
       'postcss-pxtorem': {
         rootValue: 75, // 1rem 等于多少 px（对应 JS 里的逻辑）
         propList: ['*'], // 所有属性都转换
       }
     }
   }
   ```

   ---

   **5. 补充：解决“大屏过大”问题**

   在 iPad 或 PC 端打开 H5 页面时，如果简单使用 `rem` 或 `vw`，元素会变得巨大无比。
   **解决方法：给容器设置最大宽度。**

   ```css
   body {
     max-width: 540px; /* 通常设置一个中间值 */
     margin: 0 auto;
   }
   /* 如果是 rem 布局，还需要限制 root font-size 的最大值 */
   ```

   ---

   **总结：我该选哪个？**

   | 方案               | 优点                                | 缺点                                 | 建议                                   |
   | :----------------- | :---------------------------------- | :----------------------------------- | :------------------------------------- |
   | **rem**            | 兼容性极好（甚至 IE），支持性最稳。 | 需要 JS 配合，且有少量计算开销。     | 需要兼容老旧手机时使用。               |
   | **vw/vh**          | 纯 CSS，符合浏览器标准，性能高。    | 无法轻松设置最大字号（需额外代码）。 | **目前的首选方案**（现代移动端环境）。 |
   | **px to Viewport** | 开发者体验最好，直接写 px。         | 需要构建工具支持（Webpack/Vite）。   | **工程化项目必用。**                   |

   **最佳实践：** 使用 **Vite/Webpack** 搭建环境，配置 **postcss-px-to-viewport**，在代码里直接按设计稿写 **px**。

3. **BFC：** 什么是 BFC（块级格式化上下文）？它能解决什么问题？

   **BFC（Block Formatting Context）**，即 **“块级格式化上下文”**。

   如果把网页想象成一本书，BFC 就是书中的一个**独立的“盒子”或“小世界”**。在这个盒子里的元素会按照特定的规则进行布局，而且**盒子内部的元素布局绝不会影响到盒子外部的元素**，反之亦然。

   ---

   **一、 怎样才能触发（开启）BFC？**

   只要给一个 HTML 元素加上以下任一 CSS 属性，它就会变成一个 BFC：

   1.  **`overflow`**: 值不是 `visible`（常用 `hidden`、`auto`）。
   2.  **`display`**: 值为 `inline-block`、`flex`、`grid`、`table-cell`。
   3.  **`position`**: 值为 `absolute` 或 `fixed`。
   4.  **`float`**: 值不是 `none`。
   5.  **`display: flow-root`**: (现代浏览器方案，专门为了触发 BFC 且无副作用)。

   ---

   **二、 BFC 能解决什么问题？（三大核心应用）**

   **1. 解决外边距重叠（Margin Collapse）**

   *   **现象：** 在同一个 BFC 下，两个垂直相邻的块级元素，它们的 `margin-top` 和 `margin-bottom` 会发生重叠，取其中较大的值。
   *   **解决方法：** 把其中一个元素包裹在另一个 BFC 容器中。
   *   **原理：** 因为 BFC 是独立的，不同 BFC 之间的子元素不会发生 margin 重叠。

   **2. 清除浮动（清除父元素高度塌陷）**

   *   **现象：** 当子元素全部设置了 `float` 时，父元素因为不包含浮动流，高度会变成 0（塌陷）。
   *   **解决方法：** 给父元素开启 BFC（比如设置 `overflow: hidden`）。
   *   **原理：** 计算 BFC 的高度时，浮动子元素的高度也会参与计算。这是触发 BFC 的最常用场景之一。

   **3. 防止文字环绕 / 实现两栏布局**

   *   **现象：** 一个元素浮动后，它后面的普通流元素会钻到浮动元素的下面，文字会环绕着它排版。
   *   **解决方法：** 给后面那个不浮动的元素开启 BFC。
   *   **原理：** BFC 的区域不会与浮动（float）元素的区域重叠。开启 BFC 后，它会变成一个矩形块，自动躲开旁边的浮动元素。

   ---

   **三、 BFC 的布局规则（内部运作机制）**

   了解 BFC 的内部规则，有助于理解它为什么能解决上述问题：
   1.  **内部盒子垂直排列：** 内部的 Box 会在垂直方向一个接一个地放置。
   2.  **垂直间距由 margin 决定：** 属于同一个 BFC 的两个相邻 Box 的 margin 会发生重叠。
   3.  **基准线对齐：** 每个元素的左外边距（margin-left）紧贴着包含块的左边框。
   4.  **独立隔离：** BFC 是页面上的一个隔离的独立容器，容器里面的子元素不会影响到外面。
   5.  **计算高度包含浮动：** 计算 BFC 的高度时，浮动元素也参与计算。

   ---

   **总结**

   BFC 就是一个**“结界”**。
   *   当你遇到**父元素高度丢了**（高度塌陷）、
   *   **两个盒子粘在一起分不开**（Margin 重叠）、
   *   或者**文字被图片压住了**（环绕问题），

   **开启 BFC（通常用 `overflow: hidden` 或 `display: flow-root`）往往是解决问题的“银弹”。**

5. **盒模型：** `box-sizing: border-box` 和 `content-box` 的区别是什么？

   `box-sizing` 属性决定了浏览器如何计算一个元素的 **总宽度** 和 **总高度**。

   简单来说，它们的区别在于 **“你设置的 width 到底包含哪些部分”**。

   ---

   ### 1. content-box（标准盒模型 - 默认值）
   这是 W3C 标准的默认行为。当你设置 `width` 时，它只指向**内容区域**的宽度。

   *   **计算公式：**
       `实际占据的总宽度 = width + padding + border`
   *   **表现：**
       如果你给一个元素设置了 `width: 100px`，然后再增加 `padding: 20px`，那么这个盒子的总宽度会变成 **140px**（100 + 20 + 20）。
   *   **缺点：**
       这种方式非常不直观。在做复杂布局（比如百分比布局）时，增加一点边距或边框就会把盒子“撑大”，导致布局换行或错位。

   ---

   ### 2. border-box（怪异盒模型 / IE 盒模型）
   这是目前前端开发中最常用的模型。当你设置 `width` 时，它包含了 **内容 + 内边距 + 边框**。

   *   **计算公式：**
       `实际占据的总宽度 = width` （内边距和边框会向内挤压内容区）
   *   **表现：**
       如果你给一个元素设置了 `width: 100px`，然后再增加 `padding: 20px`，盒子的总宽度**依然是 100px**。只不过里面的内容区域被压缩变小了。
   *   **优点：**
       **非常符合直觉。** 无论你加多少 padding 或 border，盒子在页面上占据的大小永远是你设定的那个 `width`。这让响应式布局和栅格系统变得非常容易控制。

   ---

   ### 3. 直观对比举例

   假设我们要写一个盒子：
   ```css
   .box {
     width: 200px;
     height: 200px;
     padding: 20px;
     border: 10px solid black;
   }
   ```

   | 属性                 | `content-box` (默认)  | `border-box` (推荐) |
   | :------------------- | :-------------------- | :------------------ |
   | **内容区宽高**       | 200 x 200             | 140 x 140           |
   | **实际占据的总宽度** | 200+40+20 = **260px** | **200px**           |
   | **实际占据的总高度** | 200+40+20 = **260px** | **200px**           |

   ---

   ### 4. 为什么现在大家都用 `border-box`？

   在早期的 CSS 中，默认是 `content-box`。这导致了程序员在写代码时必须不断地做减法。例如：
   > “我想让两个 50% 宽度的盒子并排，但它们有 10px 的边框。那我必须写 `width: calc(50% - 20px)`。”

   如果使用了 `border-box`，你只需要写 `width: 50%`，剩下的交给浏览器去向内计算。

   ### 最佳实践
   现在的绝大多数项目，都会在 **CSS Reset（重置样式表）** 中全局开启 `border-box`：

   ```css
   * {
     box-sizing: border-box;
   }
   ```
   这样可以确保全站的 UI 组件表现一致，极大降低了布局计算的难度。

6. **数据类型：** JS 有哪些基本数据类型？如何准确判断一个变量是否为数组（Array）？

7. **闭包：** 什么是闭包？请举一个闭包在实际开发中的应用场景。

   关于闭包，我是这么理解的：简单来说，闭包就是一个函数能够“记住”并访问它出生时所在的那个环境，即使这个函数是在它原本的环境之外被调用的。

   在 JS 里，当我们在一个函数内部又定义了一个子函数，并且这个子函数引用了父函数的变量，当父函数执行完后，按理说它的变量应该被销毁，但因为子函数还在引用它们，这些变量就会被保存在内存里。这就是闭包。

   在实际开发中，我用得比较多的场景是**模拟私有变量**。比如我写一个功能模块，不希望外部随意修改我内部的一个状态值，我就会用闭包把这个变量“藏”起来，只暴露一些特定的方法去操作它。

   另外一个非常经典的场景是**防抖（debounce）或者节流（throttle）**。比如防抖函数，我们需要在闭包里维护一个 timer 变量，这样每次事件触发时，内部函数都能访问到同一个定时器变量，从而实现“清除旧定时器、开启新定时器”的功能。

   当然，用闭包的时候我也比较注意，因为这些变量会一直占着内存不释放，如果用得太杂或者没处理好引用，可能会导致内存泄漏，所以我会确保在不需要的时候及时把引用置为 null。

8. **异步处理：** `Promise.all` 和 `Promise.race` 的区别是什么？如果其中一个 Promise 报错了，`Promise.all` 会如何处理？

   这两者的主要区别在于它们对“结果”的关注点不同。

   简单来说，**`Promise.all` 关注的是“全部完成”**。它接收一个 Promise 数组，只有当数组里所有的 Promise 都成功（Fullfilled）了，它才会返回一个包含所有结果的数组。这在我们需要等待多个互不依赖的请求全部拿到数据后再渲染页面时非常有用。

   而 **`Promise.race` 关注的是“谁跑得快”**。就像赛跑一样，数组里哪一个 Promise 最先改变状态（不管是变成成功还是失败），`Promise.race` 就会直接返回那个最先出来的结果，剩下的就不会管了。这个通常用来给请求做超时处理，比如让一个接口请求和一个 `setTimeout` 去比赛。

   关于你提到的**报错处理**：
   `Promise.all` 有一个“**一秒变脸**”或者说“**快速失败**（Fail-fast）”的机制。如果数组里有一个 Promise 报错了，整个 `Promise.all` 就会立即进入 `reject` 状态，并且只返回第一个报错的那个原因。即便其他的 Promise 还在进行中或者已经成功了，`Promise.all` 整体也算失败了。

   在实际项目中，如果我们希望即使有一个报错，剩下的结果也能拿回来，我通常会配合 `Promise.allSettled` 来使用，或者在每个子 Promise 后面先自己写一个 `.catch` 把错误消化掉。

9. **深浅拷贝：** 如何实现一个深拷贝（Deep Clone）？请写出简易版递归实现代码或说明注意事项（如循环引用）。

   关于深浅拷贝，最核心的区别在于：浅拷贝只拷贝一层，如果是对象或数组，它拷贝的是内存地址（引用）；而深拷贝会递归地把所有嵌套的对象都重新创建一份，实现完全的隔离。

   在实际开发中，如果数据结构比较简单，我通常会用 `JSON.parse(JSON.stringify(obj))` 这种“黑科技”，它代码最少，能解决 90% 的问题。但它有明显的硬伤：它会丢掉函数（Function）、丢掉 `undefined`、没法处理正则（RegExp）和日期（Date），最致命的是它遇到**循环引用**会直接报错。

   如果面试官让我手写一个比较严谨的深拷贝，我会用递归来实现。代码逻辑大概是这样的：

   ```javascript
   function deepClone(obj, hash = new WeakMap()) {
       // 1. 先排除基本类型和 null
       if (obj === null || typeof obj !== 'object') return obj;
   
       // 2. 处理循环引用：如果这个对象已经拷贝过了，直接从缓存（hash）里拿
       if (hash.has(obj)) return hash.get(obj);
   
       // 3. 初始化拷贝后的容器（判断是数组还是普通对象）
       let cloneObj = Array.isArray(obj) ? [] : {};
       
       // 4. 将当前对象存入 WeakMap 缓存
       hash.set(obj, cloneObj);
   
       // 5. 递归拷贝属性
       for (let key in obj) {
           if (obj.hasOwnProperty(key)) {
               cloneObj[key] = deepClone(obj[key], hash);
           }
       }
       return cloneObj;
   }
   ```

   这里面我有几个细节需要特别说明一下：
   第一，**循环引用**。如果对象 A 里面有个属性指向 B，B 又指向 A，递归就会陷入死循环导致栈溢出。所以我引入了 `WeakMap` 来记录已经拷贝过的对象，一旦发现重复就直接返回，这能有效解决循环引用的问题。
   第二，**使用 WeakMap 而不是 Map**。因为 `WeakMap` 是弱引用，它不会阻止垃圾回收机制回收原对象，这样可以避免内存泄漏。
   第三，**兼容性**。这个简易版能处理对象和数组。如果还要处理更复杂的 `Date`、`RegExp` 或者 `Symbol`，我会在递归开始前加一些特殊的 `if` 判断进行单独处理。

   总之，深拷贝的精髓就是：**递归扫描 + 类型判断 + 解决循环引用**。

10. **原型链：** 简述 JavaScript 的原型继承机制。

    JavaScript 的原型继承其实就是一种“**对象指向对象**”的机制。

    简单来说，在 JS 里，几乎所有的对象都有一个隐藏属性叫 `__proto__`（也就是原型），它指向另一个对象。当我们访问一个对象的属性或方法时，如果它自己身上没有，浏览器就会顺着这个 `__proto__` 去它的原型对象里找。如果还没找到，就继续往原型的原型找，直到找到最顶层的 `Object.prototype`。如果到最后还是找不到，就会返回 `undefined`。这一串连接起来的链条，就是我们常说的**原型链**。

    这里面有两个核心概念我通常会这样区分：

    第一，**`prototype` 和 `__proto__`**。只有函数（Function）才有 `prototype` 属性，它是用来给实例对象提供公共方法和属性的“仓库”；而所有的对象（包括函数）都有 `__proto__`，它指向创建它的那个构造函数的 `prototype`。

    第二，**继承的本质是“共享”而非“拷贝”**。原型继承不像 Java 那样通过类去完全克隆一份属性，而是通过原型链进行“引用”。这样做最大的好处是**省内存**，因为所有的实例都可以共用原型上的同一个方法，而不需要每个实例都去创建一遍。

    虽然现在我们在项目里都用 ES6 的 `class` 和 `extends` 来写继承，看起来像传统面向对象语言了，但其实它们只是**语法糖**，底层运行的逻辑依然是这套原型链机制。理解了原型，就理解了 JS 是如何实现代码复用和逻辑组织的。

11. **事件循环：** 简述一下事件循环，然后请描述宏任务（Macrotask）和微任务（Microtask）的执行顺序。

    JavaScript 是单线程的，为了在处理耗时操作（比如网络请求、定时器）时不卡死页面，它设计了一套管理异步任务的执行机制，这就是**事件循环（Event Loop）**。

    简单来说，主线程就像一个不停运转的传送带，它先处理同步代码。当遇到异步任务时，会把它挂起交给对应的模块处理，等异步任务有了结果，就会被扔进“任务队列”里排队，等主线程空闲了再去执行。

    关于**执行顺序**，这里最关键的一点是区分**宏任务（Macrotask）**和**微任务（Microtask）**：

    1.  **宏任务**：通常指 `setTimeout`、`setInterval`、I/O 操作、DOM 事件等。
    2.  **微任务**：最典型的就是 `Promise.then`、`async/await`（本质也是 Promise）以及 `MutationObserver`。

    **具体的执行流程是这样的：**

    首先，程序会执行当前的**同步代码**（这其实可以看作第一个宏任务）。
    当同步代码执行完，主线程不会立刻去拉下一个宏任务，而是先去**清空微任务队列**。只要微任务队列里有任务，它就会一个接一个地执行完，直到队列变空。
    微任务全部清空后，浏览器可能会进行页面渲染。
    最后，主线程才会从宏任务队列里取出**一个**宏任务开始执行。
    这个宏任务执行完后，主线程又会回头看微任务队列有没有新产生的任务，循环往复。

    **总结一句话：** 每次执行完一个宏任务后，必须先清空所有的微任务，才能开始下一个宏任务。

    你可以把它想象成在银行柜台办业务：柜台前排队的一个个客户就是**宏任务**；而每个客户办完主业务后，柜员问“您顺便要不要开个短信通知？”这种随手办的小业务就是**微任务**。柜员必须把当前客户所有的微任务都办完了，才能叫下一个号（执行下一个宏任务）。

12. **防抖与节流：** 请分别解释防抖（Debounce）和节流（Throttle）的区别，并手写他们的简单实现。

    关于防抖和节流，虽然它们都是为了控制函数执行的频率，但核心的“节奏感”是不一样的。

    **防抖（Debounce）** 的逻辑是：**“等在那儿，直到你停下来。”** 就像电梯门一样，如果有人一直进电梯，门就不会关，只有等最后一个人进完，等几秒钟没人再进了，门才会关上。
    在代码里，它的特点是**重置定时器**。只要你在规定的时间内再次触发，我就把之前的定时器删了，重新开始计时。这最适合用在**搜索框输入**（等用户打完字再发请求）或者**窗口大小调整（resize）**。

    **节流（Throttle）** 的逻辑是：**“按固定的节奏执行。”** 就像打游戏的技能冷却（CD）一样，不管你狂点多少次鼠标，技能也只能每隔几秒放一次。
    在代码里，它的特点是**判断锁状态**。在规定时间内，只生效第一次触发，剩下的全部无视，直到这个周期结束。这最适合用在**滚动加载（scroll）**或者**防止按钮多次点击**。

    ---

    下面是我的手写实现，我通常会用闭包来维护这个状态：

    ### 1. 防抖（Debounce）实现
    ```javascript
    function debounce(fn, delay) {
        let timer = null; // 维护一个定时器
        return function(...args) {
            // 如果在 delay 时间内再次触发，就清掉之前的，重新计时
            if (timer) clearTimeout(timer);
            timer = setTimeout(() => {
                fn.apply(this, args); // 确保 this 指向正确，并传递参数
            }, delay);
        }
    }
    ```

    ### 2. 节流（Throttle）实现（定时器版本）
    ```javascript
    function throttle(fn, delay) {
        let timer = null; 
        return function(...args) {
            // 如果已经有定时器在跑了，说明还在 CD 中，直接无视这次触发
            if (timer) return;
            
            timer = setTimeout(() => {
                fn.apply(this, args);
                timer = null; // 执行完了，把锁打开
            }, delay);
        }
    }
    ```

    这里我多提一点细节：在实现时，我会用 `apply` 来绑定 `this`，并且通过 `...args` 透传参数，这样这个防抖或节流函数就能完美适配任何业务逻辑了。

13. **生命周期：** 请描述 Vue 实例从创建到销毁的主要生命周期钩子，以及在 `created` 和 `mounted` 中分别适合做哪些操作？

    关于 Vue 的生命周期，我通常把它看作一个 Vue 实例从“出生”到“消亡”的四个阶段。

    **第一个阶段是创建前后（Creation）：**
    在 `beforeCreate` 时，实例刚初始化，数据监测（Data Observer）还没开始，拿不到 `data`。到了 **`created`**，Vue 已经完成了数据观测、属性和方法的运算，这时候我们可以访问 `data` 和 `methods` 了，但页面还没渲染，**DOM 还没生成**。

    **第二个阶段是挂载前后（Mounting）：**
    `beforeMount` 之后，Vue 会开始编译模板。最核心的是 **`mounted`**，这时候实例已经挂载到了真实的 DOM 上。如果你去看这个钩子，你会发现 `el` 已经被创建出来了，用户已经能看到页面了。

    **第三个阶段是更新前后（Updating）：**
    只要 `data` 里的数据变了，就会触发 `beforeUpdate`。等 Vue 重新渲染并打好补丁（Patch）后，会进入 `updated`。

    **第四个阶段是销毁前后（Destruction）：**
    在 Vue 3 里叫 `beforeUnmount`（Vue 2 是 `beforeDestroy`），这时实例还是完全可用的。最后是 `unmounted`，这时所有的事件监听、子实例都会被卸载。

    ---

    关于 **`created`** 和 **`mounted`** 的区别和应用，我平时是这样划分的：

    **在 `created` 中：**
    我主要用来做**初始数据的获取（API 请求）**。因为这时候 `data` 已经可以操作了，尽早发请求能缩短白屏时间。此外，一些不需要操作 DOM 的初始化逻辑，比如初始化定时器、读取本地缓存（LocalStorage）等，也会放在这里。

    **在 `mounted` 中：**
    我主要处理**涉及 DOM 的操作**。比如我要获取某个元素的高度、初始化一个 ECharts 图表、或者是实例化一个 Swiper 轮播图。因为这些第三方插件往往需要绑定真实的 DOM 节点，如果在 `created` 里执行，就会因为找不到元素而报错。

    **总结一下：** 只要不涉及 DOM，逻辑尽量往前挪，放在 `created`；只要必须碰 DOM，就老老实实等 `mounted`。这也是我在开发中保持代码健壮性的一个小原则。

14. **组件通信：** Vue 中父子组件、兄弟组件、跨层级组件通信分别有哪些方式？

    关于 Vue 的组件通信，我通常会把它们分成三个层次来处理：

    ### 第一层次：父子组件通信
    这是最常用的场景。我的做法是：**父传子用 `Props`，子传父用 `$emit`（自定义事件）**。
    如果父组件想直接调用子组件的方法，我会用 **`ref`** 获取子组件实例。在 Vue 2 里，我还可能会用到 **`.sync`** 修饰符来实现双向绑定，但在 Vue 3 里它已经被并入 `v-model` 了。

    ### 第二层次：兄弟组件通信
    这种场景下，组件没有直接的继承关系。
    在 Vue 2 里，我通常会用一个简单的 **`EventBus`**（事件总线），通过一个全局的 Vue 实例来统一 `$on` 和 `$emit`。
    而在 Vue 3 里，因为官方取消了 `EventBus`，我通常会选择引入像 **`mitt`** 这种轻量级的库，或者直接把状态提升到它们共同的父组件里，通过父组件当中转站。

    ### 第三层次：跨层级组件通信
    如果层级非常深（比如爷爷传给孙子，或者更深），用 Props 逐层传递（Props Drilling）会非常痛苦。
    我最推荐的方式是 **`provide / inject`**。父辈组件通过 `provide` 提供数据，子孙组件无论在哪一层，只要 `inject` 就能拿到。这在写一些 UI 插件或者复杂的通用组件时特别好用。

    ### 终极方案：全局状态管理
    当然，如果整个项目的多个模块都要共享一套数据（比如登录的用户信息、全局配置），我就会直接上 **`Vuex`**（Vue 2）或者 **`Pinia`**（Vue 3）。这时候组件之间就不再互相传数据了，大家都去同一个仓库（Store）里取，这样逻辑最清晰，也最容易维护。

    **总结一下：**
    *   **父子**：用 Props / Emit / Ref / v-model；
    *   **兄弟**：用事件总线、Mitt 或状态提升；
    *   **跨级**：用 Provide / Inject；
    *   **全站共享**：用 Vuex 或 Pinia。

    我在开发中会根据数据的影响范围来选择，尽量不用太重的工具来处理简单的父子通信。

15. **computed 与 watch：** 请简述两者的区别及适用场景。

    关于 `computed` 和 `watch`，虽然它们都具备监听数据变化并作出反应的能力，但它们的本质逻辑和应用场景是完全不同的。

    **首先，核心区别在于：计算属性（computed）是“衍生”出来的，而监听器（watch）是“观察”出来的。**

    **对于 `computed`：**
    它的逻辑更像是**数学公式**。我通常用它来把一个或多个原始数据加工成一个新的值。比如我有单价和数量，我通过 `computed` 计算总价。
    它有两大优势：
    1.  **缓存性**：只有当它依赖的数据变了，它才会重新计算。如果数据没变，它就会直接从缓存里拿旧的值。这在处理高频率渲染时性能非常好。
    2.  **声明式描述**：它是一个计算出来的“结果”，我们可以像用 data 里的属性一样在模板里直接用它。

    **对于 `watch`：**
    它的逻辑更像是**一个回调函数（Callback）**。当某个数据变了，我需要在这个变化发生后去做一些事情。比如当搜索关键词变了，我去调一个接口，或者去修改其他的变量。
    它的特点是：
    1.  **副作用处理**：它没有缓存。它主要用来处理异步操作，或者是在数据变了之后执行一些复杂的业务逻辑，比如打印日志、本地存储操作、或者异步请求 API。
    2.  **深度监听**：它可以配合 `deep: true` 监听对象内部属性的变化，或者是 `immediate: true` 在初始化时就先跑一遍。

    ---

    **在实际场景中，我是这样选的：**

    *   如果我想**精简模板逻辑**，比如根据性别返回不同图标、根据数组长度返回状态文字，或者对列表进行过滤搜索，我一定会选 **`computed`**。因为代码更短、逻辑更清晰且有性能缓存。
    *   如果我想在数据变化后**干点别的事儿**，比如当 URL 参数变了我要重新请求后端数据、当表单填错了我要弹出个警告弹窗，或者我要监听路由变化，我就会选 **`watch`**。

    总结成一句话就是：**如果一个值受多个值影响，用 computed；如果一个值变了要影响一堆事（特别是异步的事），用 watch。**

16. **v-if 与 v-show：** 两者有什么区别？在什么样的情况下性能更优？

17. 关于 `v-if` 和 `v-show`，它们的共同点是都能控制元素的显示和隐藏，但底层的实现方式和性能策略是截然不同的。

    **最核心的区别在于：`v-if` 是“真实的销毁与创建”，而 `v-show` 只是“CSS 的隐藏”。**

    **对于 `v-if`：**
    它是真正的**条件渲染**。当条件为 `false` 时，Vue 根本就不会把这个组件或元素插入到 DOM 树里。只有当条件变成 `true`，它才会去渲染。
    它的优点是**初始渲染开销小**。如果初始条件就是 `false`，它什么都不干，省了初始化成本。
    但缺点是**切换开销大**。每次条件切换，Vue 都要完整地执行一次 DOM 销毁和创建的过程，这会引起页面的重排和重绘。

    **对于 `v-show`：**
    它不管初始条件是什么，都会先把元素渲染出来并插入 DOM。它只是简单地通过 CSS 的 `display: none` 来控制显隐。
    它的优点是**切换开销极小**。仅仅是修改一个 CSS 属性，不会引起元素的销毁和重建。
    但缺点是**初始渲染开销大**。无论用不用得到，它都会先被渲染出来占着地方。

    ---

    **在实际场景中，我是这样选择的：**

    *   如果这个元素在页面中**频繁切换**（比如下拉菜单、标签页切换、弹窗），我一定会选 **`v-show`**。因为频繁操作 DOM 的开销太高，CSS 切换是最快的。
    *   如果这个元素**在运行时很少改变**（比如根据用户权限显示不同的操作区），或者它是一个**非常重的组件**（有很多复杂的子组件），我就会选 **`v-if`**。因为这样可以保证页面在初始加载时只加载必要的部分，减轻浏览器的负担。

    **总结一下：** 追求切换性能选 `v-show`，追求初次加载性能选 `v-if`。如果一个组件极其庞大，用 `v-if` 还能通过懒加载（Lazy Load）节省不少内存。

19. **Key 的作用：** 在 `v-for` 循环中，为什么推荐使用唯一的 `key`？如果不写会有什么后果？

20. 关于 `v-for` 中的 `key`，它的核心作用是给 Vue 的 **Diff 算法** 提供一个“**唯一身份证**（Unique Identifier）”。

    简单来说，Vue 的 Diff 算法是用来比较旧的 DOM 和新的 DOM，找出最小的变动并更新。如果没有这个 `key`，Vue 在处理列表变化（比如你在数组中间插入了一个新元素）时，它会采用一种“**就地复用**（In-place Patch）”的策略。

    **如果不写 `key`，会有两个严重的后果：**

    1.  **性能损耗较大**：没有 `key` 时，Vue 会尽可能地复用同一个位置的元素。当你插入一个新项，Vue 可能会把后面的元素一个个重新渲染（Patch），而不是简单地移动位置。有了 `key`，Vue 就能一眼认出哪个元素是哪个，只需把它挪个地方，大大减少了 DOM 操作。
    2.  **出现非预期的状态错误**：这是最致命的。比如你有一个列表，每一项都有一个 `input` 框。如果你在中间插入了一行，由于 Vue 复用了原来的 DOM 节点，你可能会发现新插入的那一行竟然带着原本属于下一行的数据或输入状态。这是因为 Vue 只是更新了文本，但没有更新 DOM 节点的生命周期。

    ---

    **在实际场景中，我是这样处理 `key` 的：**

    我通常会绑定**后台返回的 ID**（比如 `id: 101`）。这是最稳妥的，因为这个 ID 是唯一的，且不会随着顺序改变。

    我**非常不建议使用 `index`（索引）作为 key**。因为如果你在数组中间增加或删除元素，原本索引为 1 的项会变成索引为 2，这会导致 Vue 误认为这两个元素不一样，从而触发不必要的重新渲染。甚至在处理动画或复杂状态时，用 `index` 还是会遇到上面提到的状态错乱问题。

    **总结一下：** `key` 就是为了告诉 Vue：“**这个节点是我，那个节点是你，别认错了。**”它是提升 Diff 效率和保证组件状态正确的“压舱石”。

### 第四部分：工程化与 MVC

19. **MVC 与 MVVM：** 结合 JD 要求的 MVC 思想，谈谈你对 MVC 和 MVVM（Vue 所采用模式）的理解和区别。

    关于 MVC 和 MVVM，我理解它们的核心目标是一致的，都是为了**实现 UI 界面和业务逻辑的分离**，让代码更容易维护。

    **首先说一下传统的 MVC：**
    它是 **Model（模型）**、**View（视图）** 和 **Controller（控制器）**。
    在这种模式下，它们的通信通常是单向的。比如用户在 View 上点了个按钮，这个操作会传给 Controller，Controller 去处理逻辑并命令 Model 更新数据，最后 Model 再把新数据通知给 View 去刷新。
    在早期的前端开发（比如 jQuery 时代）中，这种模式很常见。但它有个痛点：**View 和 Model 的耦合度还是比较高**，开发者往往需要写大量的 DOM 操作代码来手动同步数据和界面。

    **然后再说 Vue 采用的 MVVM：**
    它是 **Model**、**View** 和 **ViewModel**。
    最大的变化就在这个 **ViewModel** 上。它就像是一个“超级管家”，通过 **数据双向绑定（Data Binding）** 自动把 Model 和 View 关联起来。
    在 MVVM 中，我们作为开发者，**几乎不需要再手动去操作 DOM 了**。我只要改变 Model 里的数据，View 就会自动跟着变；用户在 View 里的输入，Model 也会自动更新。这就是我们常说的“数据驱动视图”。

    **如果要说这两者最本质的区别，我觉得有两点：**

    第一，**自动化程度不同**。MVC 里的同步往往是手动的、命令式的；而 MVVM 是自动的、响应式的。ViewModel 帮我们把最繁琐的“找节点、改状态、更新界面”的工作全做掉了。

    第二，**职责边界更清晰**。在 MVVM 里，View 是完全不认识 Model 的，它只跟 ViewModel 沟通。这种彻底的解耦让前端组件化变得非常简单，也让逻辑测试变得更容易。

    虽然 JD 里提到了 MVC 思想，但我认为在现代前端开发中，即便我们用的是 Vue 这种 MVVM 框架，其底层依然保留了 MVC **“关注点分离”** 的优良传统。理解了 MVC 的分层逻辑，能帮我更好地规划 Vue 项目里的模块结构，比如把通用的业务逻辑抽离成独立的 Service 层（类似 Controller），而不仅仅是把所有东西都堆在组件里。

20. **Git 操作：**
    
    *   如何撤销一次已经 commit 但还未 push 的提交？
    * 在多人协作中，遇到代码冲突（Conflict）你会如何处理？
    *   关于 Git 的这些操作，我在实际工作中是这样处理的：
    
        **首先是撤销已 commit 但未 push 的提交：**
        这种场景下，我最常用的命令是 **`git reset --soft HEAD~1`**。
        这条命令的妙处在于，它只会撤销 commit 这个动作，但**保留你所有的代码改动**，放在暂存区（Staged）里。这样我就可以在修改一点代码或者重新写一段 commit message 后，再次提交。
        如果我连改动的代码都不要了，想直接回到之前的状态，我就会用 `git reset --hard HEAD~1`，但这要非常小心，因为它会直接抹掉那些没提交的代码。
    
        **然后是关于多人协作中的代码冲突（Conflict）：**
        遇到冲突是常有的事。我的标准流程是这样的：
    
        1.  **先拉取最新的代码**：在提交之前，我会先执行 `git pull`（或者先 `fetch` 再 `rebase/merge`）。
        2.  **定位冲突文件**：当 Git 提示我有冲突时，我会去编辑器（通常是 VS Code）里找那些标记了红色的文件。
        3.  **分析并解决**：我会仔细对比“我的改动（Current Change）”和“别人的改动（Incoming Change）”。如果两边逻辑不冲突，我就合并；如果别人改了同一个地方，我会拉上那个同事快速沟通一下，确认哪部分逻辑是最终需要的，然后手动删除 Git 生成的冲突标识（比如那些 `<<<<<<<` 和 `=======`）。
        4.  **重新提交**：解决完所有冲突后，我会执行 `git add .` 将文件标为已解决，然后再 `git commit`。
        5.  **最后 Push**：确保本地测试通过后，再把代码推送到远端仓库。
    
        **我的一个小建议：** 为了减少冲突，我在开发中会坚持**“频繁拉取、小步提交”**。如果我发现某个文件被很多人改动，我会尽快完成我的那部分逻辑并及时合并到主分支，避免任务拖太久导致最后的冲突变成“灾难”。这也是我在团队协作中保持高效率的一个习惯。
    
21. **性能优化：** 请列举至少 5 种前端性能优化的手段（从加载、渲染、代码编写等角度）。

23. 关于前端性能优化，我通常会从**加载速度**、**渲染效率**和**代码逻辑**这几个维度来入手。

    以下是我在实际项目中经常使用的 5 种优化手段：

    **第一，资源加载优化：**
    我会使用**路由懒加载（Route Lazy Loading）**。在 Vue 项目里，我会用 `import()` 动态加载组件，这样首屏只会加载当前路由需要的代码，而不会一次性把整个 JS 文件塞给浏览器，大大提升了白屏加载速度。

    **第二，静态资源压缩与合并：**
    我会配置 Webpack 或 Vite 进行 **Gzip 压缩**，或者使用像 **CDN（内容分发网络）** 来托管常用的库（比如 Vue 或 Element UI）。这能让文件变小，并利用 CDN 的地理位置加速和浏览器缓存机制。

    **第三，图片优化：**
    在处理大量图片时，我会使用**图片懒加载（Image Lazy Loading）**。只有当图片出现在视口内时才去请求加载。同时，我会尽量使用 WebP 格式，或者是配合阿里云/腾讯云这种 OSS 服务，直接请求缩放后的缩略图，而不是原图。

    **第四，渲染性能优化（防抖与节流）：**
    对于那些高频触发的 DOM 事件，比如 `scroll`、`resize` 或者输入框搜索，我会套上一层**防抖（Debounce）或节流（Throttle）**。这能极大地减少函数的执行频率，避免浏览器因为频繁计算和重排（Reflow）导致页面卡顿。

    **第五，代码编写层面的优化：**
    我会非常注意 **V-for 循环中的 key** 的使用，以提升虚拟 DOM 的 Diff 效率。同时，如果有的数据只是用来展示、不需要响应式追踪（比如巨大的静态列表），在 Vue 2 里我会用 `Object.freeze()` 冻结它，在 Vue 3 里我会用 `shallowRef`，这样能减少 Vue 对数据的监听开销，节省内存。

    **最后多提一个细节：** 在部署时，我会开启 **HTTP 强缓存（Cache-Control）** 和协商缓存，并配合文件名哈希（Hash）来控制版本。这样只要文件没变，用户下次访问几乎是秒开。

    这就是我平时在项目中会重点关注的几个优化方向。

24. **兼容性：** 处理线上兼容性问题。请列举你遇到过的 1-2 个浏览器兼容性问题（PC 或 H5 均可）及其解决方案。

25. 关于线上兼容性，我遇到过两个比较深刻的问题。

    ### 第一个是移动端 H5 里的“1px 边框”问题。

    在一些高清屏（Retina 屏）上，由于设备的物理像素比（DPR）是 2 甚至 3，如果你在 CSS 里直接写 border: 1px solid #ccc;，在手机上看会显得特别粗，不像设计稿里的那么精致。

    **我的解决方案是：** 使用 **CSS 伪元素（::after）+ Transform 缩放**。具体做法是给容器加一个相对定位，然后给伪元素设置绝对定位，宽高设为 200%，边框设为 1px，最后用 transform: scale(0.5); 把它缩回到原来的一半大小。这样渲染出来的边框就是真正的物理 1px，效果非常细腻。

    ### 第二个是 iOS 微信内置浏览器里的“日期格式 NaN”问题。

    在开发一个倒计时功能时，我发现代码在安卓上跑得好好的，但在 iPhone 上显示的是 NaN:NaN。排查后发现，iOS 的 Safari 内核不支持 new Date('2023-10-10 12:00:00') 这种带横杠的字符串格式。

    **我的解决方案是：** 把横杠替换成斜杠。在传给 new Date() 之前，先用正则做一下处理：dateString.replace(/-/g, '/')。这样转换成 2023/10/10 格式后，iOS 就能够正常解析了。

    ### 总结

    处理这些问题，我通常会先定位是**样式兼容性**还是**脚本兼容性**。对于样式，我会用 **PostCSS 的 Autoprefixer** 自动补全前缀，或者用 Flex 布局替代老旧的浮动布局；对于脚本，我会配置 **Babel** 转换 ES6+ 语法，并引入 **Polyfill**（补丁）来支持那些老旧浏览器缺失的 API（比如 Promise 或 Array.includes）。这样能保证大部分用户都能得到一致的体验。

23. **数组去重：** 请用 ES6 的方法对数组 `[1, 2, 2, 3, 4, 4, 5]` 进行去重。
    在 ES6 中，最简洁、最常用的方法是利用 **Set** 数据结构结合 **扩展运算符（...）**。

    代码直接写就是：

    ```JavaScript
    const arr = [1, 2, 2, 3, 4, 4, 5];
    const uniqueArr = [...new Set(arr)]; 
    // 结果：[1, 2, 3, 4, 5]
    ```

    我之所以在开发中首选这种做法，是因为 **Set** 是 ES6 新增的一种集合类型，它天然的特性就是“**成员的值都是唯一的**”。先把数组丢进 Set 自动去重，再用 ... 展开运算符把它转回数组，逻辑非常清晰，而且代码只有一行。

    当然，如果不想用展开运算符，用 **Array.from(new Set(arr))** 效果也是一样的。

    **不过我通常会多留意一点：** 这种方法处理数字、字符串等基本类型非常完美，但如果数组里面存的是**对象（Object）**，它是没法直接去重的，因为对象的引用地址不同，Set 会认为它们是不同的元素。这种情况下，我就需要配合 filter 或者 Map 来手动根据某个唯一标识（比如 ID）来去重了。

24. **URL 参数解析：** 写一个函数，将 URL 字符串参数解析为一个对象。

    *   输入：`https://example.com?name=zhangsan&age=18`
    * 输出：`{ name: 'zhangsan', age: '18' }`
    *   关于解析 URL 参数，我通常会用最现代的 **`URLSearchParams`** API。

        这是目前最简洁、最标准的方法：

        ```javascript
        function parseUrlParams(url) {
            const paramsStr = url.split('?')[1]; // 先拿到问号后面的那串
            const searchParams = new URLSearchParams(paramsStr);
            const obj = {};
            
            // 遍历每一个键值对，把它存进对象
            for (const [key, value] of searchParams) {
                obj[key] = value;
            }
            return obj;
        }
        ```

        或者，如果面试官想考察我对**数组方法**的熟练度，我会用传统的 `split` 配合 **`reduce`** 来写：

        ```javascript
        function parseUrlParams(url) {
            const paramsStr = url.split('?')[1];
            if (!paramsStr) return {};
        
            return paramsStr.split('&').reduce((acc, current) => {
                const [key, value] = current.split('=');
                acc[key] = decodeURIComponent(value); // 这里加个 decodeURIComponent 解决中文乱码
                return acc;
            }, {});
        }
        ```

        **这两个版本的区别在于：**

        1.  **现代版（URLSearchParams）**：代码可读性极高，而且它会自动帮我们处理各种边缘情况，是现在开发中的首选。
        2.  **兼容版（reduce）**：它不依赖现代浏览器的 API，在所有环境下都能跑。我在写这个版本时特意加了 `decodeURIComponent`，因为实际业务中，URL 里的中文通常会被编码，解码后才能拿到正确的原始数据。

        这两者我都会写，但在现代 H5 开发中，我更倾向于第一种，因为它更符合现代 JS 的规范。

25. **UI 逻辑实现：**
    * 题目：给定一个按钮，点击后需要每隔 1 秒在控制台打印数字，打印 5 次后停止。请写出代码。

    *   关于这个需求，我会用 `setInterval` 配合一个计数器来实现。

        代码实现大概是这样的：

        ```javascript
        const btn = document.querySelector('#myButton');
        
        btn.onclick = function() {
            // 1. 为了防止重复点击开启多个定时器，点击后可以先禁用按钮
            btn.disabled = true;
        
            let count = 0;
            // 2. 开启定时器
            const timer = setInterval(() => {
                count++;
                console.log(count);
        
                // 3. 达到 5 次后清除定时器并恢复按钮
                if (count === 5) {
                    clearInterval(timer);
                    btn.disabled = false; 
                }
            }, 1000);
        };
        ```

        **这里我有几个细节处理点：**

        第一，**状态锁**。在实际业务中，如果用户连续狂点按钮，会瞬间开启好几个定时器，导致控制台打印错乱。所以我加了一个 `btn.disabled = true` 的逻辑，在动画执行期间禁用按钮，等结束后再恢复，这样最稳妥。

        第二，**闭包的应用**。这里的 `count` 和 `timer` 变量都被包裹在点击事件的回调函数里，形成了一个闭包。这样即使点击事件结束了，内部的定时器依然能准确地访问和修改这两个变量。

        第三，**清除定时器**。我一定会记得在达到 5 次时调用 `clearInterval`。如果不清除，这个定时器会一直跑下去，造成内存泄漏，这是开发中必须要注意的规范。

        当然，如果项目里用了 **ES6+**，我也可以用 `async/await` 配合一个 `sleep` 函数来写，那样代码的可读性会像同步代码一样直观，但对于这种简单的定时任务，`setInterval` 已经非常高效了。
