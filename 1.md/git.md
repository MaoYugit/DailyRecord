## git

### 一、 必考的“双胞胎”命令对比（展现你的基础扎实度）

这是 Git 面试中含金量最高、必问的两个对比题。

#### 1. `git merge` vs `git rebase` (变基) —— 经典中的经典
*   **面试官想听到的本质区别**：
    *   **`merge`（合并）**：会将两个分支的历史汇合在一起，并生成一个新的 Merge Commit。它的优点是**真实保留了所有的提交历史和分支拓扑结构**；缺点是历史记录会变得像蜘蛛网一样复杂。
    *   **`rebase`（变基）**：会把你当前分支的提交“剪切”下来，重新“粘贴”到目标分支的最顶端。它的优点是**能得到一条干净、线性的提交历史**；缺点是它**重写了提交历史**（改变了 commit hash）。
*   **你的实战使用准则（高分项）**：
    “在实际开发中，我遵循的黄金准则是：**绝不在公共分支（如 main/develop）上使用 rebase！** 我通常在自己的个人 feature 分支上开发时，如果主分支有了更新，我会用 `git rebase main` 来拉取最新代码并保持我分支的线性；但当我开发完毕要合并回主分支时，我会向团队提交 PR（Pull Request），或者使用 `git merge --no-ff` 来强制生成一个节点，这样方便以后回溯这个功能的所有修改。”

#### 2. `git reset` vs `git revert` —— 搞砸了怎么办？
*   **面试官考点：安全的回退机制**。
    *   **`revert`（撤销）**：是**安全**的操作。它会创建一个**新的 commit**，这个新 commit 的内容刚好和你要撤销的那个 commit 相反。它**不改变现有的历史**，非常适合用在**已经推送到远程仓库的公共代码**回退。
    *   **`reset`（重置）**：是**危险**的操作。它直接把 HEAD 指针移回过去的某个节点，历史记录会被抹除（相当于时间倒流）。只适用于**尚未推送到远程的本地提交**。
*   **追问预判：`reset` 的三个参数 `--soft`、`--mixed`、`--hard` 的区别？**
    *   `--soft`：只回退 commit 信息，代码修改保留在暂存区（Index）。（适合合并多次混乱的本地 commit）。
    *   `--mixed`（默认）：回退 commit 和暂存区，代码修改保留在工作区。
    *   `--hard`：**毁灭性打击**。commit、暂存区、工作区的修改全部丢弃，完全恢复到指定版本。（慎用！）

### 二、 日常开发中的“急救”场景（展现你的丰富经验）

作为面试官，我最喜欢问：“你在工作中遇到过什么 Git 难题？怎么解决的？”你可以抛出这三个高级指令：

**场景 1：代码写了一半，突然要切分支去修线上紧急 Bug 怎么办？**
*   **你的回答**：我会使用 **`git stash` (暂存)**。它能把我当前工作区未提交的修改存到一个栈里，让工作区变得干净。然后我就可以安心切换到 hotfix 分支修 Bug。修完回来，再用 `git stash pop` 把之前的代码恢复出来继续写。

**场景 2：B 分支上有个特别好的功能提交（或者修了个 Bug），我想把它“偷”到 A 分支，但不想合并整个 B 分支？**

*   **你的回答**：使用 **`git cherry-pick <commit-hash>` (摘樱桃)**。它可以精准地只把某一个特定的 commit 应用到当前分支上，在跨分支修复特定 Bug 时极其好用。

**场景 3：刚刚 commit 完，发现漏删了一个 `console.log`，或者 commit message 拼写错了，不想再多生成一个无意义的 commit 怎么办？**
*   **你的回答**：使用 **`git commit --amend` (追加提交)**。把漏掉的代码改好并 `add` 之后，执行这个命令，它会把当前改动合并到上一次的 commit 中，保持历史整洁。

### 三、 团队协作：说说你们的 Git Flow 工作流（展现架构思维）

如果你能主动聊聊团队规范，我会把你当做未来团队的骨干（Tech Lead）来考虑。

*   **你的回答模板**：
    “我们团队有一套标准的 Git 规范。主要分支分为：
    1.  `master/main`：生产环境的稳定代码，保护分支，只能通过合并 PR 进来。
    2.  `develop`：日常开发的主分支。
    3.  `feature/*`：我们每个人接到需求，都会从 develop 拉出 feature 分支，开发完毕后提 MR (Merge Request) 进行 Code Review，通过后再合并回 develop。
    4.  `hotfix/*`：线上出现紧急 Bug，直接从 master 拉取，修复后同时合并回 master 和 develop。
    同时，我们结合了 Husky 和 Lint-staged，在 `pre-commit` 阶段强制做 ESLint 检查，在 `commit-msg` 阶段通过 commitlint 规范提交信息的格式（比如必须以 `feat:`、`fix:`、`docs:` 开头）。”

### 四、 终极加分项：Git 的底层原理是什么？（区分神仙候选人）

如果面试到了尾声，你想留下一击必杀的印象，可以主动提一句底层原理。

*   **降维打击回答**：
    “很多人以为 Git 是像 SVN 一样保存每次文件的**差异（Diff/Delta）**。但其实 Git 底层是一个**基于键值的极简文件系统**。Git 核心不是存差异，而是存**快照（Snapshot）**。
    每次提交时，Git 会对整个项目的所有文件做一次快照。如果文件没变，Git 只会保留一个指向之前存过文件的链接；如果文件变了，就存储全新的文件。它的底层依靠三种核心对象来运转：**Blob 对象（文件内容）**、**Tree 对象（目录结构）** 和 **Commit 对象（提交信息和指向 Tree 的指针）**。这也是为什么 Git 分支切换极快的原因——因为切换分支本质上只是改变了 HEAD 指针的指向，而不必像 SVN 那样去重新计算差异应用。”

如果在面试中你能把 Git 聊出上述的层次：**从危险指令的区别（rebase/reset），聊到抢救指令（stash/cherry-pick），再升华到团队规范（Git Flow/规范化提交），最后落地到快照原理**。那么这道关于 Git 的面试题，你不仅拿了满分，还会让面试官觉得你是一个极其靠谱、可以放心把核心代码库交给你管理的高级工程师。
