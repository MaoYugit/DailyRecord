这一章是 Vue 3 + TypeScript 开发的**灵魂**。

如果你用 TS 写项目，却还在到处用 `any`，或者发完请求后 `res.data.` 后面全靠猜，那你写的只是“带后缀名的 JavaScript”。

**目标：** 实现**“点”出来的代码**。当你打出 `res.data.` 时，IDE 会自动提示 `username`、`age`，并且告诉你它是 string 还是 number。

---

### 第一部分：理解数据结构层级

在写类型定义前，我们必须厘清**三层包装**：

1.  **Axios 包装** (`AxiosResponse`)：
    *   包含 `status`, `headers`, `config`, `data`。
    *   *我们在拦截器里通常会把它剥掉，只留 data。*
2.  **后端通用包装** (`ApiResponse`)：
    *   包含 `code`, `message`, `data` (这是后端程序员写的)。
3.  **业务实体数据** (`User`, `Order`)：
    *   这是真正的干货，放在后端的 `data` 字段里。

**我们的目标：** 使用**泛型 (Generics)**，把这三层打通。

---

### 第二部分：定义通用响应接口

在 `src/types/` 下新建 `api.d.ts` (或者直接写在 request.ts 里)。

这是后端和前端的**契约**。假设后端返回的格式永远是 `{ code: 200, msg: "ok", data: ... }`。

```typescript
// src/types/api.d.ts

// 1. 定义通用的后端响应结构
// T 是一个泛型，代表“具体的数据类型”
export interface ApiResponse<T = any> {
    code: number;
    message: string;
    data: T; // 这里是最关键的，T 决定了 data 长什么样
}
```

### 第三部分：封装泛型请求方法 `request<T>`

回到我们的 `src/utils/request.ts`。我们要改造它，让它支持传入泛型。

**改造前（弱类型）：**
```typescript
// 返回的是 any，毫无提示
export default service;
```

**改造后（强类型）：**

```typescript
import axios, { type AxiosInstance, type AxiosRequestConfig } from 'axios';

// 引入刚才定义的接口
import type { ApiResponse } from '@/types/api';

const service: AxiosInstance = axios.create({ /*...*/ });

// ... (这里是之前的拦截器代码) ...

// 拦截器修改：确保返回的是 response.data
service.interceptors.response.use((response) => {
    return response.data; // 这里剥离了 Axios 的壳，留下了 ApiResponse
});

// 🔥 核心封装：定义一个泛型函数
// <T> 表示：调用这个函数时，请告诉我你要什么类型的数据
// Promise<ApiResponse<T>> 表示：这个函数会返回一个 Promise，解开后是 ApiResponse，里面的 data 是 T
export const request = <T = any>(config: AxiosRequestConfig): Promise<ApiResponse<T>> => {
    return service.request(config);
};

// 同时也导出 get, post 的快捷泛型方法 (可选，但推荐)
export const get = <T = any>(url: string, config?: AxiosRequestConfig): Promise<ApiResponse<T>> => {
    return service.get(url, config);
};

export const post = <T = any>(url: string, data?: any, config?: AxiosRequestConfig): Promise<ApiResponse<T>> => {
    return service.post(url, data, config);
};

export default service;
```

### 第四部分：实战 —— 定义 API 与使用

现在我们来看看效果。假设我们要写一个“获取用户信息”的接口。

#### 1. 定义业务模型 (Model)
在 `src/api/user.ts` 中：

```typescript
import { request } from '@/utils/request';

// 1. 定义 User 的形状 (DTO - Data Transfer Object)
export interface UserInfo {
    id: number;
    username: string;
    avatar: string;
    roles: string[];
}

// 2. 定义接口参数类型 (可选，但推荐)
interface LoginParams {
    mobile: string;
    code: string;
}

// 3. 写接口函数
// 关键点：request<UserInfo>
// 意思是：我期望这个请求返回的 data 字段，是 UserInfo 类型
export const getUserProfile = () => {
    return request<UserInfo>({
        url: '/user/profile',
        method: 'GET'
    });
};

export const login = (data: LoginParams) => {
    // 这里的返回值可能是 { token: string }
    return request<{ token: string }>({
        url: '/login',
        method: 'POST',
        data
    });
};
```

#### 2. 在组件中使用 (见证奇迹的时刻)

在 `.vue` 文件中：

```vue
<script setup lang="ts">
import { onMounted, ref } from 'vue';
import { getUserProfile, type UserInfo } from '@/api/user';

// 定义响应式数据，也要加上类型
const user = ref<UserInfo | null>(null);

onMounted(async () => {
    const res = await getUserProfile();
    
    // res 的类型自动被推断为 ApiResponse<UserInfo>
    
    if (res.code === 200) {
        // 🔥 这里的代码提示会非常爽！
        // 当你输入 res.data. 时，IDE 会自动列出 id, username, avatar
        user.value = res.data;
        
        console.log(res.data.username); // TS 知道它是 string
        // console.log(res.data.age);   // ❌ 报错！UserInfo 里没有 age，提前发现 Bug
    }
});
</script>
```

### ⚔️ 面试突击检查

**Q1: 为什么要在拦截器里返回 `response.data`，这对 TS 类型定义有什么影响？**
*   **答**：
    *   Axios 默认返回 `AxiosResponse<T>`，结构是 `{ data: T, status, headers... }`。
    *   如果在拦截器里 `return response.data`，那么实际返回的就是后端的数据结构（我们定义的 `ApiResponse<T>`）。
    *   所以我们在封装 `request<T>` 时，返回值类型定义为 `Promise<ApiResponse<T>>` 才能匹配上拦截器的行为。如果不解包，还得写成 `res.data.data`，类型也很难定义。

**Q2: 什么是泛型 (Generics)？在 Axios 封装中起什么作用？**
*   **答**：
    *   泛型就像是一个“类型的占位符”或“参数”。
    *   `request<T>` 中的 `T` 就像一个坑。
    *   当我们调用 `request<User>()` 时，TS 就会把所有的 `T` 替换成 `User`。
    *   作用：实现了**一份代码，多种类型**。不用为 User 写一个 request，为 Order 写一个 request，复用性极高且类型安全。

### 🟢 随堂测试 (找茬)

下面的代码有一处类型定义导致的逻辑隐患，你能看出来吗？

**定义：**
```typescript
// 后端其实返回的是: { code: 200, data: { items: [] } }
interface Product {
    name: string;
    price: number;
}
```

**使用：**
```typescript
// 开发者直接把 T 定义为了数组
const getProducts = () => request<Product[]>({ url: '/products' });

const init = async () => {
    const res = await getProducts();
    // 开发者以为 res.data 是数组，直接遍历
    res.data.forEach(item => console.log(item.name));
};
```

---
---

**答案解析：**
**隐患：** 后端返回的 `data` 里面通常还会包一层分页信息或者对象（例如 `{ items: [...], total: 100 }`），而不是直接返回数组。

*   **错误点**：`request<Product[]>` 告诉 TS `res.data` 是个数组。
*   **实际运行**：`res.data` 是 `{ items: [] }` 对象。
*   **后果**：代码写的时候不报错（因为你骗了 TS），但运行时会报 `res.data.forEach is not a function`。
*   **修正**：
    ```typescript
    interface ProductList {
        items: Product[];
        total: number;
    }
    const getProducts = () => request<ProductList>({ url: '/products' });
    ```
