### 第一部分：CSRF 攻击与防御 (跨站请求伪造)

**1. 什么是 CSRF (Cross-Site Request Forgery)?**

*   **比喻**：借刀杀人。
*   **场景**：
    1.  你登录了**银行网站** (bank.com)，浏览器存了你的 Cookie（你的身份证）。
    2.  你没关页面，又不小心点击了一个**钓鱼网站** (hacker.com) 的链接。
    3.  钓鱼网站里有一段隐藏代码，偷偷向 bank.com 发送了一个请求：`POST /transfer?to=hacker&money=10000`。
    4.  **关键点**：浏览器发现是发给 bank.com 的，于是**自动带上了你的 Cookie**。
    5.  银行后端以为是你发的，转账成功。

**2. 防御原理：Double Submit Cookie (双重 Cookie 验证)**

既然攻击者能利用浏览器“自动发送 Cookie”的特性，那我们的防御策略就是：**要求请求头 (Header) 里也带上 Token**。

*   **原理**：浏览器限制了 JS 的跨域读取能力（同源策略）。钓鱼网站虽然能让浏览器自动发 Cookie，但它**读不到** bank.com 设置的 Cookie 内容，所以它无法构造出正确的 Header。

**3. Axios 的自动防御配置**

Axios 内置了这种防御机制。只要后端配合，前端几乎不需要写代码。

**后端要做的事**：
在 Cookie 里种一个 token，比如 `XSRF-TOKEN`（注意：这个 Cookie 不能设为 HttpOnly，否则前端读不到）。

**前端 Axios 要做的事**：
Axios 会自动从 Cookie 里读取这个值，并在发请求时，把它放到 Header 里发回给后端。

如果后端用的 Key 不是标准的，你需要手动配置 Axios：

```javascript
// src/utils/request.ts

const service = axios.create({
  baseURL: '/api',
  
  // 🔥 CSRF 防御核心配置
  // 1. 告诉 Axios 去 Cookie 里找哪个 key
  xsrfCookieName: 'XSRF-TOKEN', // 默认就是这个，如果是别的要改
  
  // 2. 告诉 Axios 把读到的值放到哪个 Header 里
  xsrfHeaderName: 'X-XSRF-TOKEN', // 默认就是这个
});
```

**面试官问：** “Axios 是怎么防 CSRF 的？”
**答：** “Axios 实现了双重 Cookie 验证模式。它会自动读取 `xsrfCookieName` 指定的 Cookie 值，并将其放入 `xsrfHeaderName` 指定的请求头中。因为浏览器同源策略限制，第三方网站无法读取这个 Cookie，也就无法伪造这个 Header，从而防御了 CSRF。”

### 第二部分：XSS 攻击与防御 (跨站脚本攻击)

**1. 什么是 XSS (Cross-Site Scripting)?**

*   **比喻**：在饭里下毒。
*   **场景**：
    1.  黑客在某论坛发布了一个帖子，内容不是普通文字，而是一段代码：`<script>stealCookies()</script>`。
    2.  后端没有检查，直接存入了数据库。
    3.  其他用户打开这个帖子，浏览器把这段文字当做代码执行了。
    4.  用户的 Cookie 被偷走了。

**2. Axios 的角色 (数据转义)**

*   **发送时**：
    Axios 默认将 `data` 序列化为 JSON (`application/json`)。
    JSON 格式天然是安全的，因为它把数据当做字符串传输，而不是当做代码执行。
    *   *例外*：如果你手动拼接 HTML 字符串并发 POST，那 Axios 救不了你。

*   **接收时**：
    Axios 只是负责把数据搬运回来，**它不管数据里有没有毒**。防 XSS 的重任主要在 **Vue** 身上。

**3. Vue 的自动防御**

Vue 3 在渲染数据时极其安全：

*   **插值表达式 `{{ content }}`**：
    Vue 会自动把内容进行**HTML 转义 (Escape)**。
    如果后端返回 `<script>alert(1)</script>`，Vue 会把它渲染成纯文本 `&lt;script&gt;...`，浏览器只会显示文字，不会执行代码。

*   **危险指令 `v-html`**：
    **这是 XSS 的重灾区！**
    如果你必须渲染富文本（比如文章详情页），你必须使用 `v-html`，但这等于门户大开。

**4. 进阶防御实战：DOMPurify**

如果你必须用 `v-html`，一定要在前端进行**清洗 (Sanitize)**。

**安装**：
```bash
npm install dompurify
```

**使用**：
```vue
<script setup>
import DOMPurify from 'dompurify';
import { ref, onMounted } from 'vue';
import axios from 'axios';

const articleContent = ref('');

onMounted(async () => {
  const res = await axios.get('/article/1');
  // 假设 res.data 是: '<img src=x onerror=alert(1)>' (有毒的代码)
  
  // 🔥 在渲染前，用 DOMPurify 洗一遍
  // 它会把危险标签去掉，只保留安全的 html (如 p, div, b)
  articleContent.value = DOMPurify.sanitize(res.data);
});
</script>

<template>
  <!-- 现在安全了 -->
  <div v-html="articleContent"></div>
</template>
```

### ⚔️ 面试突击检查

**Q1: 有了 HttpOnly Cookie，还需要防 CSRF 吗？**
*   **答**：需要。
    `HttpOnly` 只是让 JS 读不到 Cookie（防 XSS 偷 Cookie），但它挡不住 CSRF。因为 CSRF 是浏览器**自动**带上 Cookie 的，它不需要读取 Cookie。

**Q2: 前后端分离项目中，Token 放在 Header 里，还会发生 CSRF 吗？**
*   **答**：**基本不会。**
    这是 Token 机制相对于 Cookie 机制的一大优势。
    因为浏览器**不会自动**把 Token 放入 Header。前端必须手写代码 `config.headers.Authorization = token`。
    钓鱼网站没办法让受害者的浏览器自动加上这个 Header。
    *注意：如果你的 Token 是存在 Cookie 里让浏览器自动带的，那依然会有 CSRF 风险。*
