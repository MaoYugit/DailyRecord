### 第一部分：核心原理 (Why & How)

#### 1. 为什么要搞两个 Token？
*   **安全与体验的平衡**。
*   **Access Token (短命)**：比如 15 分钟过期。每次请求都带。就算被黑客截获，也只能用 15 分钟。
*   **Refresh Token (长命)**：比如 7 天过期。**只用于换取新的 Access Token**。通常保存在更安全的地方（如 HttpOnly Cookie）或 LocalStorage。

#### 2. “无感”是什么意思？
用户在使用过程中，Access Token 偷偷过期了。
1.  用户点击按钮发请求 -> 失败 (401)。
2.  **前端悄悄暂停这个请求**。
3.  **前端悄悄用 Refresh Token 去换个新的 Access Token**。
4.  **前端悄悄把刚才失败的请求重新发一遍**。
5.  用户：完全没感觉，觉得系统很丝滑。

### 第二部分：并发处理 (最难点)

**场景**：
页面初始化，同时发了 3 个请求：`getUser`, `getMenu`, `getNotice`。
刚好 Access Token 过期了。
1.  `getUser` 率先返回 401。
2.  `getMenu` 紧随其后返回 401。
3.  `getNotice` 也返回 401。

**❌ 错误做法**：
三个请求都去调用“刷新 Token 接口”。导致刷新 3 次，浪费资源，甚至可能因为 Token 轮转机制导致前面的刷新失效。

**✅ 正确做法 (互斥锁 + 队列)**：
1.  `getUser` 发现 401 -> **加锁 (`isRefreshing = true`)** -> 去刷新 -> 把自己挂起。
2.  `getMenu` 发现 401 -> 看到**锁上了** -> **不去刷新** -> 把自己加入**等待队列**。
3.  `getNotice` 发现 401 -> 看到**锁上了** -> 加入**等待队列**。
4.  刷新成功 -> 解锁 -> **清空队列**（挨个通知 `getMenu` 和 `getNotice`：“Token 好了，你们重试吧”）。

### 第三部分：代码实战 (手写核心逻辑)

请直接在 `src/utils/request.ts` 中修改响应拦截器。

```typescript
import axios from 'axios';
import { useRouter } from 'vue-router'; // 或者是你自己封装的 router
// 假设你有这两个 API 和工具函数
import { refreshTokenApi } from '@/api/auth'; 
import { getToken, setToken, getRefreshToken } from '@/utils/token';

const service = axios.create({
  baseURL: import.meta.env.VITE_API_URL,
});

// --- 🔥 核心变量 ---
let isRefreshing = false; // 是否正在刷新的标记 (互斥锁)
let requestsQueue: ((token: string) => void)[] = []; // 等待队列

// 响应拦截器
service.interceptors.response.use(
  (response) => {
    return response.data;
  },
  async (error) => {
    const originalRequest = error.config;
    
    // 1. 如果是 401 错误，且不是“刷新 Token”这个接口本身报错
    // (防止刷新接口也 401 导致死循环)
    if (error.response?.status === 401 && !originalRequest._retry) {
      
      // 2. 判断是否有锁 (并发处理)
      if (isRefreshing) {
        // 🔒 如果正在刷新，则把当前请求包装成一个 Promise，放入队列
        // 等待刷新成功后，调用 resolve 触发重试
        return new Promise((resolve) => {
          requestsQueue.push((newToken) => {
            // 这里是核心：用新 Token 替换旧 Token
            originalRequest.headers.Authorization = `Bearer ${newToken}`;
            // 重新执行原请求
            resolve(service(originalRequest));
          });
        });
      }

      // 3.如果是第一个进来的请求，开启刷新流程
      originalRequest._retry = true; // 标记，防止死循环
      isRefreshing = true; // 上锁

      try {
        // 4. 调用刷新 Token 接口 (注意：这里最好用原生的 axios 或另一个实例，避免被拦截器影响)
        const { data } = await refreshTokenApi({ 
            refreshToken: getRefreshToken() 
        });

        // 5. 刷新成功
        const newAccessToken = data.accessToken;
        setToken(newAccessToken); // 保存新 Token
        
        // 5.1 修改当前请求的 Token 并重试
        originalRequest.headers.Authorization = `Bearer ${newAccessToken}`;
        
        // 5.2 🔥 遍历队列，执行所有挂起的请求
        requestsQueue.forEach((callback) => callback(newAccessToken));
        requestsQueue = []; // 清空队列

        return service(originalRequest); // 返回当前请求的结果

      } catch (refreshError) {
        // 6. 刷新失败 (Refresh Token 也过期了，或者被废弃了)
        // 救不回来了，只能强制登出
        requestsQueue = []; // 清空队列
        localStorage.clear(); // 清空本地数据
        window.location.href = '/login'; // 强制跳转 (不用 router.push 防止路由守卫死循环)
        return Promise.reject(refreshError);
      } finally {
        // 7. 解锁
        isRefreshing = false; 
      }
    }

    return Promise.reject(error);
  }
);
```

### 第四部分：代码深度解析 (面试要点)

面试官指着代码问你细节时，你要这样回答：

1.  **`requestsQueue` 存的是什么？**
    *   它存的是一个个**回调函数**。每个回调函数接收 `newToken`，然后负责修改原请求的 Header 并重新发起请求 (`service(originalRequest)`)。
    *   我在 `Promise` 内部把这个回调 push 进队列，这样 Promise 就会一直处于 Pending 状态，直到刷新成功后我执行回调，Promise 才会 Resolve。

2.  **为什么要有 `originalRequest._retry`？**
    *   这是一个安全机制。万一刷新回来的 Token 依然是无效的（后端 Bug），或者刷新接口本身配置错了，拦截器会再次拦截 401，再次尝试刷新... 形成**无限递归死循环**，浏览器会崩溃。加上这个标记，表示“这个请求我已经救过一次了，救不活就算了”。

3.  **刷新接口本身报错怎么办？**
    *   进入 `catch` 块。这意味着 Refresh Token 也失效了（用户太久没操作，或者在别的地方改密了）。这时候必须**清空队列**并**强制跳转登录页**，让用户重新登录。
