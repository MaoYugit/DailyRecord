这一章非常有趣。如果说 `XMLHttpRequest` 是古老的座机电话，Axios 是功能齐全的智能手机，那么 **Fetch API** 就是浏览器自带的“极简版手机”。

它是浏览器**原生**提供的（不用 `npm install`），语法基于 Promise，设计比 XHR 现代得多。

但是！**Fetch 有三个著名的“坑”**，这也是面试官为了测试你是否真的用过 Fetch 而专门准备的问题。

---

### 第一部分：Fetch 的基本用法与“两次 await”

#### 1. 语法直觉
Axios 是这样写的：
```javascript
const res = await axios.get('/user');
console.log(res.data); // 直接拿到 JSON
```

Fetch 是这样写的（注意看繁琐的地方）：
```javascript
const response = await fetch('/user'); // 第 1 次 await
const data = await response.json();    // 第 2 次 await
console.log(data);
```

#### 2. 为什么需要“两次 await”？（面试考原理）
这是一个非常底层的网络交互细节：

*   **第一次 await (`fetch('/user')`)**：
    浏览器只要收到了服务器的 **响应头 (Headers)**，Promise 就解决了（Resolved）。
    此时，**身体 (Body)** 可能还在传输中（比如下载一张大图，头先到了，图还没传完）。
    `response` 对象里只有状态码和头部信息，没有数据。

*   **第二次 await (`response.json()`)**：
    这是一个异步操作。它会告诉浏览器：“请继续读取剩下的流（Stream），直到把 Body 全部下载下来，并帮我解析成 JSON。”

**总结：** 第一次是“接通电话”，第二次是“听完录音并记下来”。

### 第二部分：Fetch 与 Axios 的三大核心区别（面试必考）

如果面试官问：“既然浏览器自带了 Fetch，为什么我们还要用 Axios？”
你需要从下面这 **三个“坑”** 来回答。

#### 1. 错误处理机制不同 (最著名的坑)
*   **Axios**：只要状态码不是 2xx（比如 404, 500），Axios 会自动 **Reject**，也就是会跳进 `catch` 块或者报错。
*   **Fetch**：**只要网络连接没断，它都算成功！**
    即使服务器返回 **404 Not Found** 或 **500 Error**，Fetch 也会认为请求成功了（因为服务器确实回复你了）。它只会把 `response.ok` 设为 `false`。
    **只有网络断了（断网、DNS 解析失败），Fetch 才会 Reject。**

    *   **实战修正**：
        ```javascript
        const res = await fetch('/api/user');
        if (!res.ok) {
            // 必须手动抛出错误，否则代码会继续往下跑，导致逻辑混乱
            throw new Error(`HTTP error! status: ${res.status}`);
        }
        ```

#### 2. 默认不带 Cookie
*   **Axios**：自动发送同源 Cookie，跨域时配置 `withCredentials` 即可。
*   **Fetch**：**默认不发送 Cookie**（为了隐私安全）。如果你需要做登录后的鉴权请求，必须手动加配置。
    *   `fetch(url, { credentials: 'include' })`

#### 3. 数据处理
*   **Axios**：自动把 JSON 字符串转成 JS 对象。自动把 JS 对象转成 JSON 字符串发给 Body。
*   **Fetch**：**全手动**。
    *   发请求时：必须手动 `JSON.stringify(data)`。
    *   收数据时：必须手动 `response.json()`。

### 第三部分：Fetch 实战封装 (如何让 Fetch 像 Axios 一样好用)

在企业级开发中，如果我们不想引入 Axios（为了减少包体积），我们通常会封装一个 `myFetch`。
看懂这段代码，你就完全掌握了 Fetch。

```javascript
async function myFetch(url, options = {}) {
    // 1. 默认配置处理 (解决 cookie 和 content-type 问题)
    const defaultOptions = {
        headers: {
            'Content-Type': 'application/json'
        },
        credentials: 'include' // 允许带 cookie
    };
    
    // 合并配置
    const finalOptions = { ...defaultOptions, ...options };

    try {
        // 2. 发起请求
        const response = await fetch(url, finalOptions);

        // 3. 手动处理 HTTP 错误 (解决 4xx/5xx 不报错的问题)
        if (!response.ok) {
            // 这里可以统一处理 401 跳转登录
            if (response.status === 401) {
                console.log('Token 过期，跳转登录');
            }
            throw new Error(`Request failed with status ${response.status}`);
        }

        // 4. 解析数据 (解决两次 await 问题)
        // 注意：有时后端返回空，直接 .json() 会报错，严谨点需要判断 content-length
        const data = await response.json();
        return data;

    } catch (error) {
        // 5. 统一错误捕获
        console.error('Fetch Error:', error);
        throw error;
    }
}

// 使用起来就和 Axios 一样爽了：
// const data = await myFetch('/user', { method: 'POST', body: JSON.stringify({id: 1}) });
```

### 第四部分：Fetch 的“杀手锏” —— AbortController (取消请求)

这也是面试的高级考点。
**场景**：用户点击了“搜索”，发出了请求 A。还没等 A 回来，用户又点了一次，发出了请求 B。此时我们应该**取消**请求 A，避免旧数据覆盖新数据。

*   **Axios**：早期用 `CancelToken`，现在也改用 `AbortController` 了。
*   **Fetch**：原生支持 `AbortController`。

```javascript
// 1. 创建控制器
const controller = new AbortController();
const signal = controller.signal;

// 2. 将 signal 传给 fetch
setTimeout(() => {
    // 假设 3秒后用户取消了操作
    controller.abort(); 
    console.log('请求已取消');
}, 3000);

fetch('/api/big-data', { signal })
    .then(res => res.json())
    .catch(err => {
        if (err.name === 'AbortError') {
            console.log('这是人为取消的，不是网络故障');
        } else {
            console.error('真正的报错', err);
        }
    });
```

**参考答案：**
1.  **错**。500 算请求成功，Fetch 不会走 catch，必须手动判断 `response.ok`。
2.  `JSON.stringify()`；`Content-Type`。
3.  **理由一**：Axios 自动拦截器太好用了（统一处理 Token 和报错），Fetch 要自己封装。**理由二**：Axios 自动转换 JSON 数据，省去了 `.json()` 的步骤。
