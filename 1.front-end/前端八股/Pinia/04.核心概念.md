### 第二课：定义你的第一个 Store (Options API 风格)

#### 1. 目录结构规范（实战第一步）
在企业级开发中，我们通常会在 `src` 下创建一个 `stores` 目录，专门存放所有的 Store 文件。

请在你的项目中新建文件：`src/stores/counter.ts`。

> **命名规范**：文件通常用 kebab-case（如 `user-profile.ts`），导出的钩子函数通常用 `use` 开头，以 `Store` 结尾（如 `useUserStore`）。这是 Vue 生态的约定俗成。

#### 2. 代码实现
请将以下代码复制到 `src/stores/counter.ts` 中，我们逐行解析：

```typescript
import { defineStore } from 'pinia'

// 1. 定义并导出容器
// 参数1：'counter' 是这个 Store 的唯一 ID (必填)
// 参数2：配置对象 (Options API 写法)
export const useCounterStore = defineStore('counter', {
  
  // A. State: 存储数据的地方
  // 注意：这里必须是一个箭头函数，返回一个对象！
  state: () => ({
    count: 0,
    name: 'Pinia 初学者',
    items: [] as string[] // TS 简单类型推导
  }),

  // B. Getters: 计算属性
  // 相当于 Vue 组件里的 computed，有缓存功能
  getters: {
    // 写法 1：接收 state 作为参数 (推荐，支持 TS 推导)
    doubleCount: (state) => state.count * 2,

    // 写法 2：不传参，使用 this (需要手动指定返回类型，否则 TS 可能会懵)
    // 这种写法通常用于 getter 内部访问其他 getter
    doubleCountPlusOne(): number {
      return this.doubleCount + 1
    }
  },

  // C. Actions: 业务逻辑 & 修改数据
  // 相当于 Vue 组件里的 methods
  // 注意：这里不能用箭头函数，否则 this 指向会出错！
  actions: {
    // 1. 同步修改
    increment() {
      // 在 Pinia 里，直接用 this 读写 state，不需要 mutation！
      this.count++ 
    },

    // 2. 异步修改 (模拟请求)
    async registerUser() {
      try {
        // 模拟等待 1 秒
        await new Promise(resolve => setTimeout(resolve, 1000))
        this.name = '高级开发者' // 异步回来后直接修改
        this.count = 100
      } catch (error) {
        console.error(error)
      }
    }
  }
})
```

### 3. 核心概念详解 (面向面试与开发)

#### A. `defineStore(id, options)` 的两个参数
*   **ID (`'counter'`)**:
    *   **作用**：这是 Store 的**唯一标识**。
    *   **面试考点**：Pinia 会把所有定义好的 Store 挂载到根容器上，这个 ID 就是 Key。也是 Vue DevTools 调试插件显示的名字。如果 ID 重复，可能会导致覆盖或报错。
*   **返回值**：
    *   它返回的不是 Store 对象本身，而是一个**函数**（所以我命名为 `useCounterStore`）。只有当你在组件里调用这个函数时，Store 才会被真正创建。

#### B. `state` (数据源)
*   **写法**：`state: () => ({ ... })`
*   **实战细节**：
    *   就像 Vue 组件里的 `data()` 一样。
    *   **为什么必须是箭头函数？** 为了避免**服务端渲染 (SSR)** 时的状态污染（参考下面的面试题）。并且这样设计可以让 TypeScript 更好地推导类型。

#### C. `getters` (计算属性)
*   **特点**：
    *   **缓存**：只要依赖的 State 没变，多次调用 Getter 不会重复计算，性能极佳。
    *   **只读**：不要尝试在 Getter 里修改数据。
*   **使用 `state` vs `this`**：
    *   用 `state` 参数：写起来短，类型推导最准。
    *   用 `this`：当你需要访问**其他的 Getter** 或者 **Actions** 时使用。

#### D. `actions` (动作)
*   **革命性变化**：
    *   **没有 Mutations 了！** 这是 Pinia 对比 Vuex 最大的改进。无论同步还是异步，统统在 Actions 里写。
    *   **直接修改**：`this.count++`。底层 Pinia 会通过 Proxy 监听变化并更新视图。
*   **注意**：Actions 内部**不要使用箭头函数**，因为箭头函数会绑定父级作用域的 `this`，导致你无法通过 `this` 访问到 Store 实例。

### 👹 面试官视角：这部分怎么考？

#### ❓ 面试题 1：为什么 `state` 必须是一个函数？
**答案**：
1.  **闭包/工厂模式**：如果 state 是一个纯对象 `state: { count: 0 }`，那么在服务端渲染（SSR）或者应用复用的场景下，不同的用户请求可能会共用同一个对象引用，导致数据相互污染（你看到了我的购物车）。
2.  **重置功能**：Pinia 允许通过 `store.$reset()` 快速重置状态，它是通过重新执行 state 函数拿到初始值来实现的。

#### ❓ 面试题 2：Pinia 的 Actions 和 Vuex 的 Mutations/Actions 有什么区别？
**答案**：
*   **Vuex**：
    *   Mutations：必须同步，唯一修改 state 的地方。
    *   Actions：可以异步，不能直接改 state，必须 `commit` mutation。
*   **Pinia**：
    *   **去掉了 Mutations**。
    *   Actions：既可以同步也可以异步，直接 `this.state` 修改，逻辑更符合直觉（Mental Model）。

#### ❓ 面试题 3：Actions 里能解构 state 吗？
**答案**：
可以，但不推荐直接解构基本类型。
```javascript
increment() {
  let { count } = this // ❌ 这里的 count 变成了普通数字，修改它不会影响 Store
  this.count++ // ✅ 正确写法
}
```
