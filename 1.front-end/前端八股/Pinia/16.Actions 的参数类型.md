Actions 在 TypeScript 中本质上就是**普通的函数**。所以，给它标注类型，其实就是给函数的参数和返回值标注类型。

在企业级开发中，Actions 通常承担着**“对接 API”**的重任。后端需要的参数格式是非常严格的，如果我们能把 API 参数类型定义好，就能在调用 action 时获得极其丝滑的代码提示。

---

### 第十四课：Actions 的参数类型与 API 约束

#### 1. 基础：给参数加上类型

这是最基本的操作。如果不加，TS 可能会报错（如果你开启了 `noImplicitAny`），或者将其视为 `any`（失去了检查意义）。

```typescript
actions: {
  // ✅ 基础写法：明确指定 amount 是数字
  increment(amount: number) {
    this.count += amount
  },

  // ✅ 多个参数
  // 虽然可以这样写，但参数超过3个建议合并成一个对象
  sendMessage(text: string, fromUser: string) {
    // ...
  }
}
```

---

#### 2. 进阶：API 请求参数约束 (DTO 模式)

在真实业务中，我们经常要处理“登录”、“提交表单”等操作。
**强烈建议**：不要在 action 参数里把字段一个个写出来，而是定义一个 **DTO (Data Transfer Object)** 接口。

**场景：用户登录**
后端要求 POST `/api/login` 传入 `{ username, password, captcha? }`。

**Step 1: 定义参数接口 (types/auth.ts)**
```typescript
export interface LoginPayload {
  username: string
  password: string
  captcha?: string // 验证码可选
}
```

**Step 2: 在 Action 中使用**
```typescript
import type { LoginPayload } from '@/types/auth'

actions: {
  // ✅ 参数直接引用接口
  async login(payload: LoginPayload) {
    try {
      // 1. 这里的 payload. 就会有自动提示 (username, password...)
      console.log('正在登录:', payload.username)
      
      // 2. 发送请求给后端
      // 假设 api.post 也支持泛型，那响应结果也有类型提示了
      const res = await api.post('/login', payload)
      
      this.token = res.data.token
    } catch (e) {
      console.error(e)
    }
  }
}
```

**Step 3: 在组件中调用**
```typescript
const store = useAuthStore()

// ✅ 当你输入 store.login({ ... }) 时
// VS Code 会强制要求你必须包含 username 和 password
// 少写一个属性都会爆红！
store.login({
  username: 'jack',
  password: '123'
})
```

#### 3. 高级技巧：利用 `Partial<T>` 做部分更新

**场景：更新用户信息**
后端接口 `/api/user/update`，允许你只改名字，或者只改头像，或者都改。

如果我们要为此定义好几个接口（`UpdateNameParams`, `UpdateAvatarParams`...）太累了。
我们可以利用 TS 的工具类型 **`Partial<T>`**（把所有属性变成可选）。

```typescript
import type { UserInfo } from '@/types/user'

actions: {
  // ✅ Partial<UserInfo> 意味着：
  // UserInfo 里定义的所有字段，在这里传哪几个都行，不传也行
  async updateProfile(updates: Partial<UserInfo>) {
    
    // 1. 发送请求
    await api.patch('/user', updates)
    
    // 2. 本地 State 更新
    // this.$patch 支持传入部分对象，完美契合 Partial
    this.$patch(updates)
  }
}
```

**组件调用体验：**
```typescript
// 只改名字
store.updateProfile({ name: 'Rose' }) 

// 只改年龄
store.updateProfile({ age: 18 })

// ❌ 如果传入 UserInfo 里不存在的字段，直接报错
// store.updateProfile({ gender: 'male' }) // 报错：UserInfo 类型里没有 gender
```

#### 4. 补充：Actions 的返回值类型

通常 Action 是异步的，会自动推导为 `Promise<void>`（如果没有 return）。
但有时候我们需要组件知道“操作是否成功”，或者返回后端的数据。

```typescript
// 显式标注返回类型
async fetchUser(): Promise<boolean> {
  try {
    await api.get('/user')
    return true // 成功
  } catch {
    return false // 失败
  }
}
```
*注：在 Setup Store 中，这就只是个普通的 async 函数写法，TS 自动推导一般就够了。*

### 👹 面试官/架构师 视角

#### ❓ 面试题 1：为什么建议把 Action 参数合并成一个对象（Payload）？
**答案**：
1.  **可读性**：`login({ username, password })` 比 `login('jack', '123')` 清晰得多。
2.  **扩展性**：如果后端接口加了一个“验证码”字段，我只需要修改 Interface 和 Action 内部，组件调用处如果不传验证码（设为可选）甚至不需要改代码。如果是多个参数 `login(u, p, c)`，中间插入参数会引发灾难。
3.  **类型复用**：这个 Interface 通常和 API 请求库（如 Axios）定义的参数类型是一致的。

#### ❓ 面试题 2：Setup Store 和 Options Store 在 Action 类型定义上有区别吗？
**答案**：
没有区别。
*   Options Store: `actions: { login(payload: LoginPayload) { ... } }`
*   Setup Store: `function login(payload: LoginPayload) { ... }`
这部分是纯粹的 TypeScript 函数定义知识。
