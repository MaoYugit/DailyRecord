太好了，这部分是决定你写出来的代码是被同事夸“专业”，还是被骂“甚至没入门”的分水岭。

在团队开发中，**规范 > 技巧**。Pinia 虽然很自由，但如果我们不制定规则，项目很快就会变成一团乱麻。

### 第十五课：架构设计与最佳实践

#### 1. 目录结构规范

在 Vuex 时代，我们需要构建复杂的 Module树。在 Pinia 时代，结构是**扁平化**的。

**推荐的企业级目录结构**：

```text
src/
  ├── stores/
  │   ├── index.ts        # (可选) 统一导出入口
  │   ├── user.ts         # 用户相关 (Token, Profile)
  │   ├── cart.ts         # 购物车业务
  │   ├── global.ts       # 全局配置 (Theme, Locale)
  │   └── order/          # 如果业务太复杂，可以建子文件夹
  │       ├── list.ts
  │       └── detail.ts
  ├── types/              # 专门存放 TS 类型定义
  │   └── store.d.ts
```

**关于 `index.ts` 的统一导出**：
很多教程会让你写一个 `index.ts` 把所有 Store 导出来，方便组件引用。
```typescript
// src/stores/index.ts
export * from './user'
export * from './cart'
```
**❌ 大厂实践建议：不要这样做！**
**原因**：
1.  **Code Splitting（代码分割）失效**：如果你只在某个页面用了 `UserStore`，但因为从 `index.ts` 引入，可能会导致所有 Store 的代码都被打包进这个页面（视构建工具优化程度而定）。
2.  **循环依赖地狱**：如果 `UserStore` 引用了 `CartStore`，而它们都从 `index.ts` 导出，很容易发生“先有鸡还是先有蛋”的报错。

**✅ 推荐做法**：
在组件中**按需引入**，指向具体文件。
```typescript
import { useUserStore } from '@/stores/user' // 清晰、无副作用
```

#### 2. 模块化与命名空间 (Store ID)

`defineStore('id', ...)` 里的这个 ID 必须是**全局唯一**的。
如果是多人协作，A 开发了 `menu` (侧边栏菜单)，B 开发了 `menu` (点菜菜单)，就冲突了。

**最佳实践：使用枚举 (Enum) 管理 ID**

新建 `src/stores/constants.ts`：
```typescript
export enum Names {
  User = 'USER',
  Cart = 'CART',
  Product = 'PRODUCT',
  Global = 'GLOBAL'
}
```

在 Store 定义中使用：
```typescript
import { Names } from './constants'

export const useUserStore = defineStore(Names.User, () => { ... })
```
这样，如果有人重复定义了 ID，编辑器会直接提示或报错，不用等到运行时才发现。

#### 3. 业务逻辑剥离：瘦组件，胖 Store

这是 MVVM 架构的核心原则。

*   **瘦组件 (Thin Component)**：只负责渲染 UI (Template) 和 简单的事件触发。
*   **胖 Store (Fat Store)**：负责所有的数据处理、API 请求、逻辑判断。

**❌ 错误示范 (逻辑写在组件里)**：
```html
<!-- Component.vue -->
<script setup>
const cartStore = useCartStore()

async function onCheckout() {
  // 逻辑散落在组件里，难以复用，难以测试
  if (cartStore.items.length === 0) return alert('空车')
  
  const total = cartStore.items.reduce((a, b) => a + b.price, 0)
  
  try {
    await api.post('/checkout', { total })
    cartStore.items = [] // 手动清空
    router.push('/success')
  } catch (e) {
    alert('失败')
  }
}
</script>
```

**✅ 正确示范 (逻辑封装在 Action)**：

```typescript
// src/stores/cart.ts
actions: {
  async checkout() {
    if (this.items.length === 0) throw new Error('Cart is empty')
    
    const total = this.totalPrice // 使用 getter
    await api.post('/checkout', { total })
    this.items = []
    return true
  }
}
```

```html
<!-- Component.vue -->
<script setup>
const cartStore = useCartStore()
const router = useRouter()

async function onCheckout() {
  // 组件只负责调用和跳转
  try {
    await cartStore.checkout()
    router.push('/success')
  } catch (e) {
    alert(e.message)
  }
}
</script>
```
**好处**：如果以后有另一个页面（比如“一键购买”）也要结算，直接调用 `store.checkout()` 即可，不需要复制粘贴代码。

#### 4. DevTools 调试技巧

Vue DevTools 是开发神器。一定要学会使用 **Pinia 面板**。

1.  **安装**：Chrome 商店搜索 "Vue.js devtools" (注意要安装支持 Vue 3 的版本)。
2.  **查看面板**：
    *   打开 F12 -> Vue -> 🍍 Pinia。
    *   你可以看到左侧列出了所有当前活跃的 Store。
3.  **核心功能**：
    *   **State Inspection**：点击某个 Store，右侧实时显示它的 State、Getters。你甚至可以双击修改数据，测试组件反应。
    *   **Timeline (时间旅行)**：
        *   当你修改数据或触发 Action 时，Timeline 会记录每一步操作。
        *   **Time Travel**：你可以点击旧的记录，页面会“回滚”到那个时刻的状态。这对于复现 Bug 非常有用。
    *   **Action Testing**：在组件还没写好的时候，你可以直接在 DevTools 里手动修改 State 来测试逻辑。

### 👹 面试官/架构师 视角

#### ❓ 面试题 1：什么时候该把数据放入 Pinia，什么时候放在组件内部 `ref`？
**答案**：
*   **Pinia**：跨组件共享的数据（如用户信息）、需要跨页面保持的数据（如滚动位置）、复杂的业务状态（如购物车）。
*   **组件内部 `ref`**：UI 相关的临时状态（如模态框的 `isOpen`、表单输入的临时 `inputValue`）。不要把所有东西都塞进 Store，那会导致内存浪费和 Store 臃肿。

#### ❓ 面试题 2：如何处理 Store 过于庞大的问题？
**答案**：
虽然 Pinia 只有 Store 概念，没有 Module 嵌套，但我们可以通过**文件拆分**和**组合式函数 (Composables)** 来解决。
*   **拆分**：把一个巨大的 `ProductStore` 拆分成 `ProductListStore` 和 `ProductDetailStore`。
*   **提取逻辑**：把复杂的非状态逻辑提取成独立的 `.ts` 文件或 hooks，然后在 Store 里引用。
