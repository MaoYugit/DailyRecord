### 第一部分：Pinia 知识全景图（复习速查）

在去面试前，脑海里要有这张图：

| 核心概念     | Setup Store (推荐)                 | Options Store (旧)                 | 备注                       |
| :----------- | :--------------------------------- | :--------------------------------- | :------------------------- |
| **定义**     | `defineStore(id, () => { ... })`   | `defineStore(id, { ... })`         | ID 必须全局唯一            |
| **State**    | `const count = ref(0)`             | `state: () => ({ count: 0 })`      | **必须用箭头函数**         |
| **Getters**  | `const double = computed(...)`     | `getters: { double(state) {...} }` | Setup 写法自动推导类型最强 |
| **Actions**  | `function add() { ... }`           | `actions: { add() { ... } }`       | 支持同步和异步             |
| **修改数据** | 直接 `count.value++` 或 `$patch`   | `this.count++` 或 `this.$patch`    | **没有 Mutations 了！**    |
| **解构**     | **必须用 `storeToRefs`**           | **必须用 `storeToRefs`**           | 否则失去响应式             |
| **重置**     | 手写 `$reset` 函数                 | 自带 `store.$reset()`              | 这是一个主要区别           |
| **持久化**   | 插件 `pinia-plugin-persistedstate` | 同左                               | 生产环境必备               |

### 第二部分：面试突击（夺命连环问）

这里列出的是面试官最爱问的 5 道题。我不仅给你标准答案，还教你**“高分回答”**技巧。

#### Q1: Pinia 和 Vuex 有什么区别？（必考）
**普通回答**：Pinia 是 Vuex 的替代品，去掉了 Mutations，支持 TS，体积更小。
**高分回答**（展现深度）：
1.  **架构简化**：Pinia 只有 State、Getters、Actions，**彻底抛弃了 Mutations**。因为 Vue 3 的响应式机制（Proxy）足够强大，直接修改数据也能被监听，Mutations 变得多余且繁琐。
2.  **扁平化设计**：Pinia 没有 Vuex 那种复杂的 Modules 嵌套树。每个 Store 都是独立的，按需引入，这更有利于 **Code Splitting**（代码分割）和类型推导。
3.  **TS 支持**：Pinia 原生支持 TS，自动推导极其强大；而 Vuex 4 对 TS 的支持非常痛苦。
4.  **体积**：Pinia 只有 1kb 左右，极轻量。

#### Q2: 为什么解构 Store 会失去响应式？如何解决？
**核心考点**：JS 基础与 Proxy 原理。
**回答**：
*   **原因**：Store 实例本身是一个 Proxy 对象（Reactive）。当我们 `const { count } = store` 时，其实是读取了当前的数值（比如 `0`）赋值给了局部变量 `count`。这个局部变量和 Store 里的 Proxy 已经脱钩了，所以后续变化无法追踪。
*   **解决**：使用 `storeToRefs(store)`。它会把 State 和 Getters 里的每个属性都包裹成 `ref` 对象，`ref` 会保留对源数据的引用（Reference）。
*   **注意**：Actions 不需要也不应该使用 `storeToRefs`，直接解构即可。

#### Q3: Pinia 如何实现持久化？原理是什么？
**核心考点**：插件机制与订阅。
**回答**：
*   **实战**：通常使用 `pinia-plugin-persistedstate` 插件。
*   **原理**：
    1.  利用 `pinia.use()` 注册插件。
    2.  在插件内部，通过 `store.$subscribe` 监听 State 的每一次变化。
    3.  变化发生时，使用 `JSON.stringify` 序列化数据并存入 `localStorage`。
    4.  Store 初始化时，插件会先从 Storage 读取数据，通过 `store.$patch` 恢复状态。

#### Q4: 怎么在 Pinia 中复用逻辑（类似 Vuex 的 Mixin）？
**核心考点**：Setup Store 的灵活性。
**回答**：
Vuex 复用逻辑很难，但 Pinia 如果使用 **Setup Store** 写法，复用极其简单。
我们可以把通用的逻辑（比如分页逻辑、CRUD 逻辑）封装成一个 **Composable (Vue Hooks)**，然后在 defineStore 内部直接调用这个 Hook，把返回的状态和方法 return 出去即可。这体现了 Vue 3 **“组合式 API”** 的强大优势。

#### Q5: 多个 Store 之间如何互相调用？会不会有循环依赖？
**回答**：
*   **调用**：非常简单，在一个 Store 的 Action 内部直接 `useOtherStore()` 即可。
*   **循环依赖**：如果 A 引用 B，B 又引用 A，且都在**顶层**（代码最外层）调用，会报错。
*   **解决**：确保 `useStore()` 的调用是放在 `actions` 或 `getters` 的**函数内部**，而不是文件顶部。这样只有在真正执行函数时才会去实例化，避开了初始化时的死锁。

### 第三部分：毕业实战项目 —— 《极简电商购物车》

光说不练假把式。请打开你的编辑器，用 **TS + Setup Store** 完成这个需求。

#### 1. 项目需求
你需要实现三个核心模块：
1.  **ProductStore**：商品列表（包含库存）。
2.  **UserStore**：用户信息（包含余额、优惠券）。
3.  **CartStore**：购物车逻辑（核心）。

#### 2. 具体功能点（必须实现）

*   **TypeScript**：
    *   定义 `Product` 和 `CartItem` 接口，严禁出现 `any`。
*   **展示**：
    *   页面显示商品列表，每个商品有“加入购物车”按钮。
    *   如果库存为 0，按钮禁用。
*   **交互 (Action)**：
    *   点击“加入购物车”：
        1.  `ProductStore` 库存 -1。
        2.  `CartStore` 列表里添加该商品（如果已存在，数量 +1）。
*   **结算 (跨 Store 调用)**：
    *   点击“结算”按钮：
        1.  计算总价（Getter）。
        2.  调用 `UserStore`，检查余额是否充足。
        3.  如果充足，扣款，清空购物车，弹出“支付成功”。
        4.  如果不足，弹出“余额不足”。
*   **持久化**：
    *   刷新页面，购物车里的东西不能丢（使用插件）。
