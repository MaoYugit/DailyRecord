在 TypeScript 的世界里，**推导（Inference）**是最好的朋友，但有时候它也会“罢工”，特别是在 Pinia 的 **Options API** 中使用了 `this` 的时候。

这一节我们重点解决：**Getters 什么时候会报错？怎么手动补全类型？**

---

### 第十三课：Getters 的类型推导与手动标注

#### 1. Setup Store：几乎不用管 (Easy Mode)

如果你用的是 **Setup Store** (`ref` + `computed`)，恭喜你，TypeScript 的自动推导能力在这里发挥得淋漓尽致。

```typescript
// Setup Store
export const useCounterStore = defineStore('counter', () => {
  const count = ref(10)

  // ✅ TS 自动推导 doubleCount 为 Ref<number>
  const doubleCount = computed(() => count.value * 2)

  // ✅ 即使是复杂对象，通常也能推导出来
  const user = ref({ name: 'Jack', age: 18 })
  const description = computed(() => {
    return `${user.value.name} is ${user.value.age} years old`
  }) // 自动推导为 Ref<string>

  return { count, doubleCount, description }
})
```
**结论**：在 Setup Store 中，99% 的情况不需要手动标注 Getters 类型。

---

#### 2. Options Store：**`this`** 的陷阱 (Hard Mode)

问题主要出在 **Options Store**。

Pinia 的 `getters` 有两种写法，TS 的表现截然不同：

**写法 A：接收 `state` 参数（推荐，自动推导完美）**
```typescript
getters: {
  // ✅ TS 知道 state 是什么（上一节定义过接口了）
  // 它可以自动推导出 doubleCount 是 number
  doubleCount: (state) => state.count * 2,
}
```

**写法 B：使用 `this` 访问其他 Getter（报错高发区）**
当你需要在一个 Getter 里访问另一个 Getter 时，必须用 `this`。
但是，TS 在处理对象字面量的 `this` 上下文推导时，很容易遇到**循环引用**或**推导失败**的问题。

**❌ 错误示例**：
```typescript
getters: {
  doubleCount: (state) => state.count * 2,

  // ❌ TS 报错：'this' implicitly has type 'any'...
  // 或者 TS 不知道 this.doubleCount 存在
  tripleCount() {
    return this.doubleCount + 1 
  }
}
```

**✅ 解决方案：手动标注返回类型**
你必须显式地告诉 TS，这个函数返回什么类型。一旦你标注了返回类型，TS 就能反向推导出 `this` 的上下文。

```typescript
getters: {
  doubleCount: (state) => state.count * 2,

  // ✅ 显式标注 : number
  // JSDoc 的 /** @returns {number} */ 在这里是不够的，必须用 TS 语法
  tripleCount(): number {
    return this.doubleCount + 1
  },
  
  // 如果返回的是对象，也可以引用接口
  currentUserInfo(): UserInfo | null {
    return this.userList.find(u => u.active) || null
  }
}
```

#### 3. Actions 的参数类型标注

Actions 本质上就是函数，它的类型标注和普通函数一模一样。
**重点在于参数的标注**，这决定了你在组件里调用时的提示。

```typescript
actions: {
  // 1. 简单参数
  increment(amount: number) { // 👈 必须标注，否则是 implicit any
    this.count += amount
  },

  // 2. 复杂参数 (复用之前定义的接口)
  async login(payload: { username: string; pass: string }) {
    // ...
  },
  
  // 3. 甚至可以给返回值标注 (Promise)
  async fetchUser(): Promise<boolean> {
    try {
      await api.get('/user')
      return true
    } catch {
      return false
    }
  }
}
```

### 👹 面试官/架构师 视角

#### ❓ 面试题 1：为什么 Options Store 里用 `this` 写 Getter 会推导失败？
**答案**：
这是 TypeScript 的限制。
在 `defineStore({...})` 这个巨大的对象字面量中，TS 正在尝试推导这个对象的类型。
*   TS 需要先知道 State 的类型。
*   然后推导 Getters 的类型。
*   如果在推导 Getters 时，函数内部又引用了 `this`（它指向 Store 本身，而 Store 包含了 Getters），这就形成了一个**循环依赖**。
为了打破这个循环，我们需要**显式标注返回类型**，切断推导链条，直接告诉 TS 结果。

#### ❓ 面试题 2：Setup Store 中 `computed` 需要手动标注类型吗？
**答案**：
通常不需要。但在一种情况下需要：**当你希望返回值的类型比推导结果更“宽泛”时**。
比如，你希望返回 `UserInfo | null`，但当前逻辑只返回了 `null`，TS 会推导为 `null` 类型。为了兼容性，你可以泛型标注：
```typescript
// 强制声明返回类型
const activeUser = computed<UserInfo | null>(() => {
  return null // 暂时没找到用户
})
```

### 阶段总结

*   **State**: 必须定义 Interface，杜绝 `any`。
*   **Getters (Options API)**: 用到 `this` 时，**必须**手动写 `: Type`。
*   **Actions**: 参数必须标注类型。
