

## **第一阶段：三座大山与词法规则**

如果不理解作用域，你的代码就会出现“变量莫名其妙变成了 undefined”或者“改了一个变量，导致整个页面挂了”的灵异现象。

---

### 1. 什么是作用域 (Scope)？

用最通俗的话说：**作用域就是一套规则，用来管理变量存储在哪里，以及如何找到它们。**

想象成**“权限控制”**：
*   **全局作用域**：公共广场，谁都能来拿东西。
*   **函数作用域**：私人房间，只有房间里的人能用。
*   **块级作用域**：房间里的保险箱，权限更严格。

---

### 2. JS 的“进化史”：从两种到三种

在 ES6（2015年）之前，JS 只有两种作用域。ES6 引入 `let/const` 后，才有了第三种。这是面试必问的差异点。

#### 🟢 1. 全局作用域 (Global Scope)
最外层的代码。在浏览器中，全局变量会挂载到 `window` 对象上。
```javascript
var g = "我是全局的";

function fn() {
    console.log(g); // 可以在任何地方访问
}
```

#### 🟢 2. 函数作用域 (Function Scope) —— `var` 的地盘
在函数内部定义的变量，外部是**完全看不见**的。
**注意**：`var` 只有在遇到**函数**时才会受到限制，遇到 `if` 或 `for` 的 `{}` 它是看不见的！

```javascript
function fn() {
    var a = "我是局部的";
    console.log(a); // ✅ 能访问
}

fn();
console.log(a); // ❌ 报错：ReferenceError: a is not defined
```

#### 🟢 3. 块级作用域 (Block Scope) —— `let/const` 的地盘
这是 ES6 带来的革命。**任何一对花括号 `{ ... }`**（包括 `if`, `for`, `while`, 甚至单独写的 `{}`），对于 `let` 和 `const` 来说都是一个新的作用域。

**☠️ 面试必考对比：`if` 语句里的 `var` vs `let`**

```javascript
// === var 的情况 ===
if (true) {
    var x = 100; // var 无视花括号，它觉得这还在全局里
}
console.log(x); // 😱 输出 100 (污染了全局变量！)


// === let 的情况 ===
if (true) {
    let y = 200; // let 看到花括号，就觉得自己被关起来了
}
console.log(y); // ✅ 报错：y is not defined (安全！)
```

> **结论**：在现代开发（Vue/React）中，**99% 的情况请用 `let/const`**，因为块级作用域更符合我们要的“封装”直觉，不会莫名其妙污染外部变量。

---

### 3. 核心心法：词法作用域 (Lexical Scoping)

这是整个 JS 作用域体系的**总纲**。我们在闭包里已经接触过一点了，这里正式定义它。

**定义**：**作用域是由代码写在哪里决定的，而不是由代码在哪里执行决定的。**
（也叫“静态作用域”）

#### 🌰 经典案例图解

```javascript
var value = 1;

function foo() {
    console.log(value);
}

function bar() {
    var value = 2;
    foo(); // 在这里调用 foo
}

bar();
```

**思考**：输出 `1` 还是 `2`？

*   **动态作用域（JS 没有这个）**：会想，“我在 `bar` 里调用的 `foo`，`bar` 里有 `value=2`，所以应该找 `2`”。（❌ 错误）
*   **词法作用域（JS 的规则）**：会想，“`foo` 是在**全局**定义的。它出生的时候，外面就是全局作用域。不管你在哪里调用我，我找变量只看我**出生的地方**”。（✅ 正确）

**答案**：输出 `1`。

---

### 🔍 第一阶段总结

1.  **ES6 之前**：只有全局作用域 + 函数作用域。`var` 声明的变量会穿透 `if` 和 `for` 的花括号。
2.  **ES6 之后**：引入了块级作用域（Block Scope）。`let/const` 在任何 `{}` 内都是私有的。
3.  **铁律**：JS 采用**词法作用域**。函数找变量，只往“定义位置”的外层找，不看“调用位置”。

### 🟢 1. 什么是作用域链 (Scope Chain)？

如果当前作用域里找不到你要的变量，JS 引擎该怎么办？
它会往**外层**（上一级）作用域去找。如果不还是没有，就再往外找，直到**全局作用域**。

这就形成了一条**链条**。

**通俗比喻：借钱**
1.  **当前作用域**：你只有 10 块钱。想买个 100 块的东西。
2.  **外层作用域**：你问你爸要。
3.  **再外层**：你爸也没有，问你爷爷要。
4.  **全局作用域**：爷爷也没有，那没办法了。

#### 💻 代码演示：爬楼梯

```javascript
let a = 1; // 全局 (爷爷)

function outer() {
    let b = 2; // 外层 (爸爸)
    
    function inner() {
        let c = 3; // 内层 (你)
        
        // 1. 找 c? 在自己屋里找到了 -> 3
        console.log(c);
        
        // 2. 找 b? 自己没有 -> 往上爬 -> 爸爸有 -> 2
        console.log(b); 
        
        // 3. 找 a? 自己没有 -> 爸爸没有 -> 爷爷有 -> 1
        console.log(a);
    }
    
    inner();
}

outer();
```

### 🟢 2. 变量遮蔽 (Variable Shadowing)

面试官经常问：**“如果内层变量和外层变量同名，会发生什么？”**

**规则**：**就近原则**。
一旦在当前层或者较近的层找到了变量，JS 就会**停止向上查找**。外层的同名变量被“遮蔽”了（Shadowed），你暂时看不见它。

```javascript
let name = "全局";

function fn() {
    let name = "局部"; // 这里的 name 遮蔽了 全局 name
    
    console.log(name); // 输出 "局部"
    // 在这里，你没有任何办法直接访问到那个 "全局" 的 name 变量
}

fn();
```

---

### 🟢 3. 查找失败：LHS 与 RHS（面试加分项）

当爬到顶层（全局）还没找到变量时，JS 引擎会有两种反应，取决于**你在做什么操作**。

这涉及到两个术语（不用死记，理解意思就行）：
*   **RHS (Right-hand Side)**：**查找值**（比如 `console.log(a)`，我要读取 `a` 的值）。
*   **LHS (Left-hand Side)**：**赋值**（比如 `a = 1`，我要给 `a` 赋值）。

#### 情况 A：RHS 查找失败（读不到） -> 报错
如果你想**读取**一个不存在的变量：

```javascript
console.log(notDefinedVar); 
// ❌ 报错：Uncaught ReferenceError: notDefinedVar is not defined
// 翻译：我不认识这个变量。
```

#### 情况 B：LHS 查找失败（写不进） -> 隐式全局变量（大坑！）
如果你想**赋值**给一个不存在的变量，并且**没有开启严格模式 (`'use strict'`)**：

```javascript
function fn() {
    // 忘记写 let/var/const 了！
    // JS 引擎会想：既然全局也没有，那我就好心帮你创建一个全局变量吧。
    leak = "我是个意外"; 
}

fn();
console.log(leak); // 😱 输出 "我是个意外"
console.log(window.leak); // 它变成了 window 的属性！
```

**⚠️ 实际开发警告**：
这被称为**“隐式全局变量”**，是内存泄漏和 Bug 的常见源头。
**解决方案**：永远使用 `'use strict'`（Vue/React 的脚手架默认都开启了），这样 LHS 查找失败时也会报错 `ReferenceError`。

---

### 🔍 第二阶段总结

1.  **查找方向**：从内向外（Bottom Up），直到全局。
2.  **遮蔽效应**：内层有同名变量，就用内层的，不再往外找。
3.  **结果**：
    *   读取不存在的变量 -> `ReferenceError`。
    *   给不存在的变量赋值 -> 非严格模式下会创建**全局变量**（大坑），严格模式下报错。

 **第三阶段：变量提升 (Hoisting)**。

好的，进入 **第三阶段：变量提升 (Hoisting) 与 暂时性死区 (TDZ)**。

这是面试官最喜欢用来“坑”你的环节。他们会写一段逻辑看起来完全反直觉的代码，问你输出什么。如果你不懂变量提升，绝对会掉进坑里。

---

### 🟢 1. 什么是变量提升 (Hoisting)？

你以为 JS 代码是从上到下一行行执行的吗？
**大错特错。**

在代码执行之前，JS 引擎会先进行一次 **“预扫描”（编译阶段）**。
在这个阶段，引擎会把所有的 **变量声明** 和 **函数声明** “提升”到当前作用域的**最顶端**。

---

### 🟢 2. `var` 的提升：只提名字，不提值

这是 `var` 最让人诟病的地方。

#### 💻 代码演示
```javascript
console.log(name); // 输出 undefined（而不是报错！）
var name = "Tony";
```

**为什么？**
JS 引擎在预编译时，会把代码“脑补”成这样：

```javascript
var name; // 1. 【提升】声明被挪到了最顶上，默认赋值 undefined

console.log(name); // 2. 执行：此时 name 是 undefined

name = "Tony"; // 3. 执行：赋值留在原地
```

**结论**：使用 `var` 声明变量，**可以在声明之前使用它**，但值是 `undefined`。这很容易导致 Bug。

---

### 🟢 3. 函数的提升：整体提升 (一等公民)

**函数声明 (Function Declaration)** 的待遇比变量高，它是**整个函数体**都被提升到了最顶端。

#### 💻 代码演示
```javascript
sayHi(); // 输出 "Hello!" (完全没问题)

function sayHi() {
    console.log("Hello!");
}
```

**引擎看到的：**
```javascript
// 1. 【提升】整个函数被挪到了最顶上
function sayHi() {
    console.log("Hello!");
}

sayHi(); // 2. 执行：此时函数已经存在了
```

#### ☠️ 面试陷阱：函数表达式 (Function Expression)

如果你用 `var` 定义函数，情况就变了！

```javascript
sayBye(); // ❌ 报错：sayBye is not a function

var sayBye = function() {
    console.log("Bye!");
};
```

**解析**：
这里 `sayBye` 被当作一个普通的 `var` 变量。
1.  `var sayBye` 被提升，值是 `undefined`。
2.  执行 `sayBye()` 时，相当于执行 `undefined()`。
3.  所以报错说“它不是一个函数”。

---

### 🟢 4. `let/const` 与 暂时性死区 (TDZ)

ES6 实际上**修复**了变量提升带来的怪异行为。

面试官问：**“`let` 和 `const` 存在变量提升吗？”**
标准回答：**“从技术上说，它们也被提升了（创建了），但在初始化之前无法访问。这段时间被称为‘暂时性死区’（TDZ, Temporal Dead Zone）。”**

#### 💻 代码演示
```javascript
console.log(age); // ❌ 报错：ReferenceError: Cannot access 'age' before initialization
let age = 18;
```

**什么是 TDZ？**
*   进入作用域（比如 `{}`）的一瞬间，`age` 变量就已经存在了（绑定好了）。
*   但是，直到代码执行到 `let age = 18` 这一行之前，**这块区域是“禁区”**。
*   凡是在这块禁区里碰 `age`，直接报错。

**结论**：TDZ 强迫你**必须先声明，后使用**。这是一个非常好的特性。

---

### 🔍 第三阶段总结（神图表）

| 声明方式                       | 提升 (Hoisting) | 提升内容                | 提前访问的结果        |
| :----------------------------- | :-------------- | :---------------------- | :-------------------- |
| **var**                        | ✅ 是            | 仅声明 (赋值 undefined) | `undefined`           |
| **function**                   | ✅ 是            | **整个函数体**          | **正常执行**          |
| **let/const**                  | ✅ 是 (但有锁)   | /                       | ❌ **报错 (TDZ)**      |
| **函数表达式** (`var f = ...`) | ✅ 是            | 仅变量名 (undefined)    | ❌ **报错 (不是函数)** |

### 🟢 上题揭晓：变量提升的双重陷阱

```javascript
console.log(a);  // 输出 1: undefined
var a = 1;

function test() {
    console.log(a); // 输出 2: undefined
    var a = 2;
}

test();
```

**✅ 正确答案**：两个都是 `undefined`。

**解析**：
1.  **全局**：`var a` 声明被提升，但赋值没有。所以第一行打印 `undefined`。然后 `a` 变成 1。
2.  **函数内**：**最坑的地方在这里！** 虽然外面有 `a = 1`，但函数内部写了 `var a = 2`。
    *   根据**变量提升**：内部的 `var a` 声明被提到函数顶部。
    *   根据**遮蔽原则**：内部有了 `a`，就不去管外面的 `a` 了。
    *   所以 `console.log(a)` 执行时，看到的是内部那个**已声明但未赋值**的 `a`。

如果你答对了，恭喜你，你的作用域基础已经非常扎实！

### 🟢 第四阶段：容易混淆的 `this` 与 作用域

这是 JS 中最大的“精神分裂”现场。

很多新手（甚至老手）会把 **作用域（Scope）** 和 **`this` 机制** 搞混。
*   **作用域**：是**静态**的。代码写在哪，就决定了变量能不能被访问。（词法作用域）
*   **`this`**：是**动态**的。函数**怎么被调用**，决定了 `this` 指向谁。

**一句话总结核心区别**：
**作用域看“出生地”，`this` 看“调用方”。**

---

### 1. 为什么说 `this` 是动态的？

看同一个函数，被不同方式调用，`this` 截然不同。

```javascript
function sayName() {
    console.log(this.name);
}

var name = "全局";
var obj = { name: "对象内部", fn: sayName };

// 1. 普通调用 -> this 指向 window (非严格模式)
sayName(); // 输出 "全局"

// 2. 对象调用 -> this 指向调用它的对象
obj.fn();  // 输出 "对象内部"

// 3. 强制绑定 (call/apply) -> this 指向你指定的对象
sayName.call({ name: "指定对象" }); // 输出 "指定对象"
```

> **面试考点**：`this` 的指向完全取决于**函数执行的那一刻**，是谁在“点”它。

---

### 2. 箭头函数：叛逆的“异类”

ES6 的箭头函数是面试中的重灾区。
**箭头函数没有自己的 `this`！**

那它的 `this` 是什么？
**它会“捕获”它定义时所在的作用域的 `this`。**

**👉 这意味着：箭头函数的 `this` 居然变成“静态”的了！它遵循的是词法作用域规则（看出生地）。**

#### 💻 经典对比：普通函数 vs 箭头函数

**场景**：在 `setTimeout` 中访问对象属性。

```javascript
const obj = {
    name: "Tony",
    
    // 情况 A：普通函数
    sayRegular: function() {
        setTimeout(function() {
            // 普通函数的 this 指向调用者。
            // setTimeout 的回调是在全局环境执行的，所以 this 是 window
            console.log("Regular:", this.name); 
        }, 100);
    },
    
    // 情况 B：箭头函数
    sayArrow: function() {
        setTimeout(() => {
            // 箭头函数：我不产出 this，我直接用外层的 this。
            // 外层是 sayArrow，它的 this 是 obj。
            // 所以这里能正确找到 obj
            console.log("Arrow:", this.name); 
        }, 100);
    }
};

obj.sayRegular(); // 输出 undefined (因为 window.name 是空)
obj.sayArrow();   // 输出 "Tony" ✅
```

**Vue 开发实战关联**：
这就是为什么在 Vue 2 或 React Class 组件中，我们经常在回调函数里用箭头函数，或者在顶部写 `const that = this`（老土办法）。目的就是为了**锁住 this**。

---

### 3. Vue 中的 `this` (Options API)

你在写 Vue 2 或者 Vue 3 的 Options API (`data`, `methods`) 时，为什么可以用 `this.message` 访问数据？

```javascript
export default {
    data() {
        return { message: "Hello" };
    },
    methods: {
        greet() {
            console.log(this.message);
        }
    }
}
```

**原理**：
Vue 在底层帮你做了 **硬绑定 (Hard Binding)**。
当 Vue 初始化组件时，它会遍历 `methods` 里的所有函数，利用 `bind` 把它们的 `this` 强制绑定到了当前组件实例（Proxy）上。

**⚠️ 禁忌**：
**千万不要在 `methods` 里用箭头函数！**

```javascript
methods: {
    // ❌ 错误写法
    badGreet: () => {
        // 箭头函数会去上一层找 this。
        // 在 Vue 文件里，上一层通常是 window 或者 undefined，而不是组件实例。
        console.log(this.message); // 报错或 undefined
    }
}
```

---

### 🔍 第四阶段总结

1.  **普通函数**：`this` 是**动态**的。谁调用我，我指向谁。（默认 window，点调用指对象）。
2.  **箭头函数**：`this` 是**静态**的（词法作用域）。我出生在哪里，就继承哪里的 `this`，且**无法被 `call/bind` 修改**。
3.  **核心口诀**：
    *   遇到 `function`，看前面有没有“点” `.`。
    *   遇到 `=>`，看它写在哪里（外层函数是谁）。

### 🟢 1. 作用域的“黑魔法”：`eval` 和 `with`（反面教材）

面试官可能会问：“除了写在代码里的词法作用域，有没有办法在运行时修改作用域？”

答案是**有**，但**坚决不要用**。

1.  **`eval("var a = 2")`**：
    *   它可以把字符串当代码跑。
    *   它会欺骗词法作用域，强行在当前作用域“插入”一个变量。
    *   **缺点**：极其影响性能（引擎无法优化），且有安全风险（XSS 攻击）。
2.  **`with(obj) { ... }`**：
    *   它可以把一个对象处理为一个全新的作用域。
    *   **缺点**：容易导致变量泄露到全局，代码逻辑极其混乱。严格模式（Strict Mode）已经**完全禁止**使用 `with`。

**面试满分回答**：
> “JS 有 `eval` 和 `with` 可以动态修改作用域，但它们是**性能杀手**且破坏了词法作用域规则，严格模式下也被限制，所以实际开发中绝对不使用。”

### 🟢 2. 终极总结 Cheat Sheet（复习专用）

保存这张表，面试前瞄一眼：

| 特性         | `var`                         | `let` / `const`                          |
| :----------- | :---------------------------- | :--------------------------------------- |
| **作用域**   | **函数作用域** (无视 `{}`)    | **块级作用域** (被 `{}` 锁死)            |
| **变量提升** | **有** (初始化为 `undefined`) | **有** (但在这个死区 **TDZ** 访问会报错) |
| **重复声明** | 允许 (`var a; var a;`)        | ❌ 报错 (`SyntaxError`)                   |
| **挂载全局** | 是 (`window.a`)               | 否 (不会变成 window 属性)                |

### 🔥 3. 地狱级面试题：作用域 + This + 变量提升

这是检验你是否真正毕业的最终试炼。请不要运行代码，拿纸笔画一下，写出输出结果。

```javascript
var length = 10; // 全局变量

function fn() {
    console.log(this.length);
}

var obj = {
    length: 5,
    method: function(fn) {
        fn(); // 第一步：调用传入的 fn
        
        arguments[0](); // 第二步：通过 arguments 调用 fn
    }
};

obj.method(fn, 1);
```

**😱 你的答案是？**
（提示：`arguments` 是一个类数组对象，包含了所有参数）

---

#### 💡 答案解析（高能预警）

**输出结果**：
1.  `10`
2.  `2`

**详细推导**：

1.  **第一步 `fn()`**：
    *   执行 `obj.method` 里的 `fn()`。
    *   这是一个**普通函数调用**，前面没有点 `.`。
    *   所以 `this` 指向全局对象 `window`。
    *   全局的 `length` 是 10。
    *   **输出：10**。

2.  **第二步 `arguments[0]()`**：
    *   这步最坑！`arguments` 是一个对象，长这样：`{ 0: fn, 1: 1, length: 2 }`。
    *   `arguments[0]` 拿到的就是 `fn` 函数。
    *   调用写法是 `arguments[0]()`，相当于 `arguments.0()`（虽然语法不对，但逻辑是点调用）。
    *   **重点**：谁调用的？是 `arguments` 对象点出来的。
    *   所以 `this` 指向 `arguments` 对象。
    *   `arguments` 对象有 `length` 属性吗？有！它代表参数的个数。传入了 `fn` 和 `1`，所以长度是 2。
    *   **输出：2**。

> 如果你这道题答对了（或者理解了为什么是 2），你的 `this` 和作用域知识已经超过绝大多数面试者了！🚀

### 🎓 4. 模拟面试 Q&A

**Q1: "let 和 var 的区别是什么？"**
> **参考**：
> 1.  **作用域**：`var` 是函数作用域，`let` 是块级作用域。
> 2.  **提升**：`var` 提升并初始化为 `undefined`；`let` 提升但处于 TDZ（死区），提前访问会报错。
> 3.  **全局挂载**：全局的 `var` 变量会挂在 `window` 上，`let` 不会。

**Q2: "什么是词法作用域？"**
> **参考**：
> 也可以叫静态作用域。意思是函数的作用域链在**函数定义的时候**就已经决定了，而不是在调用的时候。函数查找变量时，只看它“出生”的地方。

**Q3: "箭头函数的 this 是怎么确定的？"**
> **参考**：
> 箭头函数没有自己的 `this`。它会捕获它**定义时**所在上下文的 `this`，本质上是遵循了**词法作用域**的查找规则。
