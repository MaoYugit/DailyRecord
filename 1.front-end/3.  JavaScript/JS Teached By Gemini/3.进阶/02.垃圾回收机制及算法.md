## 第一阶段：基本原理与“引用计数”

在 C 语言或 C++ 中，开发者需要手动申请内存（`malloc`）和释放内存（`free`）。但在 JavaScript 中，引擎会自动帮我们做这件事。

那么，引擎是怎么知道**哪块内存没用了（是垃圾）**，哪块还在用呢？

---

### 🟢 1. 核心标准：可达性 (Reachability)

这是所有 GC 算法的共识：**“如果一个对象能被访问到，它就是有用的；如果访问不到了，它就是垃圾。”**

我们将内存想象成一张**蜘蛛网**：
1.  **根 (Roots)**：是这张网的中心起点。
    *   在浏览器中，根通常是 `window`（全局作用域）。
    *   以及当前正在执行的函数栈里的变量。
2.  **连接**：如果一个对象通过引用链（`obj.a`, `arr[0]`）连接到了**根**，那它就是**“可达的”**（活的）。
3.  **垃圾**：如果从**根**出发，怎么走都走不到这个对象（断联了），那它就是垃圾，会被回收。

---

### 🟢 2. 最古老的算法：引用计数 (Reference Counting)

这是最简单、最直观的垃圾回收策略。
（*注：虽然现代 JS 引擎的主流算法不是这个，但面试官经常问它的缺陷，IE6/7 的 DOM 回收也曾用过它*）

#### 🧠 原理
给每个对象挂一个“计数器”。
*   当有一个变量引用它时，计数器 `+1`。
*   当引用失效（比如变量被赋值 `null` 或函数执行完出栈）时，计数器 `-1`。
*   **回收时刻**：当计数器变成 **0** 时，说明没人引用它了，立马销毁！

#### 💻 代码演示
```javascript
// 1. 创建对象 {name: 'A'}，引用数 = 1 (被 user 引用)
let user = { name: 'A' }; 

// 2. 将引用赋给 admin，引用数 = 2 (user, admin)
let admin = user; 

// 3. user 断开引用，引用数 = 1 (admin 还在引用)
user = null; 

// 4. admin 也断开引用，引用数 = 0 
// ♻️ 触发回收，释放内存
admin = null; 
```

---

### 🟢 3. ☠️ 致命缺陷：循环引用 (Circular Reference)

这是引用计数算法最大的软肋，也是我们之前学**深拷贝**时反复提到的概念。

**场景**：如果两个对象互相引用，但它们和外界没有任何联系。

```javascript
function marry() {
    var man = {};
    var woman = {};

    // 互相引用
    man.wife = woman;
    woman.husband = man;

    return '结束';
}

marry();
// 函数执行完了，man 和 woman 局部变量被销毁了。
// 外界已经无法访问 man 和 woman 对象了（按理说是垃圾）。
```

**引用计数算法的视角**：
1.  `man` 对象：虽然外面没人指着它，但 `woman.husband` 指着它。引用数 = **1**。
2.  `woman` 对象：虽然外面没人指着它，但 `man.wife` 指着它。引用数 = **1**。
3.  **结论**：引用数都不是 0，**无法回收！**
4.  **结果**：内存泄漏。这两个对象会一直占用内存，直到浏览器关闭。

> **历史背景（面试谈资）**：
> 早期的 IE 浏览器（IE 6/7）中，JS 引擎是用标记清除，但 DOM 对象是用引用计数的。
> 所以，如果你在 JS 里写了 `dom.onclick = function() { ... }`，而这个 function 内部又引用了 `dom`，就会形成 DOM 和 JS 对象的循环引用，导致严重的内存泄漏。这也是当年 jQuery 能够大火的原因之一（它内部帮你处理了很多这种坑）。

---

### 🔍 第一阶段总结

1.  **垃圾的定义**：无法从根（Root）触达的对象。
2.  **引用计数法**：
    *   **优点**：简单，发现 0 就删，回收非常及时。
    *   **缺点**：**无法解决循环引用**。互相引用的孤岛对象永远不会被回收，导致内存泄漏。

---

**🔥 第一阶段测试题：**
现代浏览器（Chrome/Firefox）还会有“循环引用导致内存泄漏”的问题吗？

好的，进入 **第二阶段：现代标准——“标记-清除” (Mark-and-Sweep)**。

首先揭晓上一阶段测试题的答案：
**现代浏览器（Chrome/Edge/Firefox）已经完全解决了循环引用的内存泄漏问题。**
因为它们不再使用“引用计数”算法，而是采用了一种更聪明的算法——**标记-清除**。

---

### 🟢 1. 核心思想：从“根”出发，活要见人死要见尸

这个算法把内存管理变成了一个“连连看”的游戏。

它不关心对象被引用了多少次（哪怕是 10000 次），它只关心：**“从根节点（Roots）出发，能不能摸到这个对象？”**

#### 🔍 算法流程（两步走）

1.  **标记阶段 (Mark)**：
    *   垃圾回收器会从 **根 (Roots)**（全局对象 window、当前执行栈）开始遍历。
    *   只要是能从根顺藤摸瓜找到的对象，都被打上一个 **“活动” (Reachable)** 的标记。
    *   （这就像是从根节点倒了一桶红油漆，沿着引用连线流，沾到油漆的就是活的）。

2.  **清除阶段 (Sweep)**：
    *   遍历整个堆内存。
    *   凡是身上**没有标记**的对象，统统视为垃圾。
    *   直接销毁，释放内存。

---

### 🟢 2. 完美解决“循环引用”

回到上一阶段那个让“引用计数”崩溃的例子：

```javascript
function marry() {
    var man = {};
    var woman = {};
    man.wife = woman;
    woman.husband = man;
}
marry();
```

**标记-清除算法是怎么处理的？**

1.  **函数执行前**：`man` 和 `woman` 在函数作用域内，可以通过执行栈访问到。**打标：活着**。
2.  **函数执行结束**：
    *   函数作用域销毁，执行栈弹出。
    *   此时，全局的根（window）无法找到 `man`，也无法找到 `woman`。
    *   **关键点**：虽然 `man` 和 `woman` 互相指着对方，但**没有人指着他们俩**。
    *   从根出发的“油漆”流不到他们这里。
3.  **结果**：两个对象都没有标记 -> **清除**。

> **结论**：孤岛（Island）再大、内部连接再复杂，只要跟大陆（Root）断了连，就是死路一条。

---

### 🟢 3. 进阶优化：标记-整理 (Mark-Compact)

面试官可能会追问：**“清除之后会有什么问题吗？”**

#### ⚠️ 内存碎片化 (Memory Fragmentation)
想象一下，你有一排柜子（内存），刚才清理了一些垃圾，现在的状态是：
`[空] [东西] [空] [空] [东西] [空]`

虽然空出来的总空间很大，但都是**零零散散**的。
如果现在来了一个巨大的对象（需要连续 3 个格子），虽然总空位够，但**连续的空间**不够，就放不下。

#### ✅ 整理 (Compact)
为了解决这个问题，现代算法在“清除”之后，通常会多做一步**“整理”**：
*   把所有活着的对象，向内存的一端移动（紧凑排列）。
*   `[东西] [东西] [空] [空] [空] [空]`
*   这样右边就留出了一大片连续的空闲内存。

---

### 🔍 第二阶段总结

1.  **现代标准**：所有现代 JS 引擎（V8, SpiderMonkey 等）都使用 **标记-清除**（及其变种）。
2.  **逻辑**：
    *   **Mark**：从根递归查找，标记所有活对象。
    *   **Sweep**：清除没标记的死对象。
    *   **Compact**：整理内存碎片，让活对象紧凑排列。
3.  **优势**：彻底解决了循环引用的泄漏问题。

---

**🔥 思考时间：**
既然“标记-清除-整理”这么好，那能不能每隔几毫秒就跑一次？反正电脑快。
不行！因为 GC 运行时，为了防止内存变化，通常会**暂停 JS 代码的执行**（这叫 **Stop-The-World**，全停顿）。

如果内存里有几百万个对象，遍历一遍要很久，页面就会**卡顿**。
Chrome 的 **V8 引擎** 是怎么解决“卡顿”问题的？

回复**“进入第三阶段”**，我们要学习 V8 的**分代回收策略**（新生代 vs 老生代），这是面试中区分“初级”和“高级”的分水岭！



欢迎来到 **第三阶段：V8 引擎的优化——“分代回收” (Generational Collection)**。

这一阶段是面试中区分“只会背书”和“真正理解底层”的分水岭。

为什么要有分代回收？
因为**“全停顿” (Stop-The-World)** 实在是太卡了。如果 JS 堆里有 1GB 的数据，每次 GC 都要从头到尾扫一遍，浏览器直接卡死 500ms，用户体验就崩了。

V8 引擎的设计师发现了一个**黄金定律（弱分代假说）**：
> **“绝大部分的对象都是‘朝生夕死’的，只有极少部分对象会长久存活。”**

于是，V8 把内存分成了两个世界：**新生代 (New Space)** 和 **老生代 (Old Space)**，对它们使用完全不同的算法。

---

### 🟢 1. 新生代 (New Space) —— “快进快出”

*   **特点**：生存周期短，容量小（通常只有 1MB ~ 8MB）。
*   **住户**：你函数里临时的变量、循环里的 `let i` 等。
*   **算法**：**Scavenge 算法（切尼算法 - Cheney's Algorithm）**。

#### 🧹 怎么回收？（复制法）
V8 把新生代空间一分为二：
1.  **使用区 (From-Space)**：正在用的。
2.  **空闲区 (To-Space)**：空的。

**流程**：
1.  当 **使用区** 快满时，触发垃圾回收。
2.  **标记**：找出“使用区”里所有**活着**的对象。
3.  **复制**：把活的对象有序地**复制**到“空闲区”。（死对象不管它，直接留在原地）。
4.  **交换**：原来的使用区清空变成空闲区，原来的空闲区变成使用区。

**优缺点**：
*   ✅ **极快**：因为大部分对象都是死的，需要复制的活对象很少。
*   ✅ **无碎片**：复制过去时是紧凑排列的。
*   ❌ **空间浪费**：必须要有一半空间是空的（典型的**用空间换时间**）。

---

### 🟢 2. 对象晋升 (Promotion)

一个对象如果命很大，在新生代里经过了多次回收居然还没死，V8 就会觉得：“嗯，你是个老家伙了，别在新生代里挤占位置了，去老生代吧。”

**晋升条件**：
1.  **熬过一劫**：已经经历过一次 Scavenge 回收，还活着。
2.  **占比过高**：To-Space 内存占用超过 25%（防止把老生代撑爆）。

---

### 🟢 3. 老生代 (Old Space) —— “稳重持久”

*   **特点**：生存周期长，容量大（几百 MB 到几 GB）。
*   **住户**：全局对象、闭包引用的变量、DOM 节点。
*   **算法**：**标记-清除 (Mark-Sweep) + 标记-整理 (Mark-Compact)**。

#### 🧹 怎么回收？
这里不能用“复制法”了，因为老生代对象太多、太大，复制起来太慢，而且浪费一半空间太心疼。

所以这里用的是我们**第二阶段**学的标准算法：
1.  **标记**：遍历引用链，标记活的。
2.  **清除**：清理死的。
3.  **整理**：把活的挤在一起，解决内存碎片。

---

### 🟢 4. 极致优化：增量标记 (Incremental Marking)

即使分了代，如果老生代非常大，遍历一遍还是要很久，导致页面卡顿。

V8 引入了 **增量标记**：
*   **原理**：把巨大的 GC 任务切成很多个小任务。
*   **执行**：JS 跑一会儿 -> GC 跑一点 -> JS 再跑一会儿 -> GC 再跑一点...
*   **效果**：虽然 GC 总时间没变（甚至略长），但**分散**到了各个帧里，用户感觉不到卡顿了（平滑）。

---

### 🟢 5. 实战应用：WeakMap (弱引用)

讲 GC 必须提 `WeakMap`，这是 ES6 专门为内存管理设计的。

**场景**：我想给一个 DOM 元素存一些额外数据，但不想影响它被回收。

```javascript
// ❌ 强引用：Map
const map = new Map();
let btn = document.getElementById('btn');

map.set(btn, { clicked: true }); 

// 即使 btn 元素从 DOM 树移除了，btn = null 了
// map 依然引用着 btn 对象，导致它无法被 GC 回收！
```

```javascript
// ✅ 弱引用：WeakMap
const weakMap = new WeakMap();
let btn = document.getElementById('btn');

weakMap.set(btn, { clicked: true });

// btn 被移除，btn = null
// WeakMap 是“弱”的，GC 会忽略 weakMap 对 btn 的引用。
// btn 对象会被直接回收，weakMap 里的这条数据也会自动消失。
```

> **总结**：`WeakMap` 的键（Key）必须是对象，且是弱引用。一旦键对象没有其他引用，就会被 GC 悄悄收走，**防止内存泄漏**。

---

### 🎓 终极总结 (Cheat Sheet)

如果面试官问：“请讲一下 V8 的垃圾回收机制”，你可以这样满分回答：

1.  **总策略**：V8 采用**分代回收**策略，将内存分为**新生代**和**老生代**。
2.  **新生代**：
    *   存放生命周期短的对象。
    *   使用 **Scavenge 算法**（复制法）。
    *   特点是**用空间换时间**，速度极快，但有一半空间闲置。
3.  **老生代**：
    *   存放生命周期长或晋升上来的对象。
    *   使用 **标记-清除-整理** 算法。
    *   特点是**不浪费空间**，但速度较慢。
4.  **优化**：为了避免全停顿（Stop-The-World），V8 使用了**增量标记**，将 GC 任务切片执行，保证页面流畅。
5.  **补充**：我们在开发中可以使用 `WeakMap` 来持有对象的弱引用，避免内存泄漏。
