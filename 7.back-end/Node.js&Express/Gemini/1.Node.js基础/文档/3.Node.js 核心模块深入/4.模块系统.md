## **十一、模块系统 (Module System)**

这部分内容是Node.js编程的**组织基础**。如果说`fs`, `path`, `http`是建造房子的“砖块”、“水泥”和“水电管道”，那么模块系统就是“建筑图纸和施工规范”，它告诉你如何合理地组织和划分代码，让你的项目从一个小茅屋，有潜力扩展成一栋摩天大楼。

在前端，你可能已经非常熟悉ES Modules (`import`/`export`)。而在Node.js的世界里，你必须先掌握它的“原生语言”——**CommonJS**。

---

### **代码的秩序 — 模块化的“创世纪”**

#### **1. 没有模块化的“洪荒时代” — `all-in-one.js` 的噩梦**

让我们进行一个思想实验。想象一下，我们正在开发一个稍微复杂一点的博客应用后端，代码全部写在同一个文件 `server.js` 里。

这个文件可能会是这样的：

```javascript
// server.js (一个没有模块化的噩梦)

// --- 数据库连接逻辑 ---
const dbHost = 'localhost';
const dbUser = 'root';
function connectToDatabase() {
  console.log(`正在连接到数据库 ${dbHost}...`);
  // ...复杂的连接代码...
  return true;
}

// --- 用户认证逻辑 ---
let currentUser = null;
function login(username, password) {
  // ...验证用户名密码...
  currentUser = { name: username };
  console.log(`${username} 登录成功!`);
}
function logout() {
  currentUser = null;
}
function checkAuth() {
  // ...检查currentUser是否存在...
}

// --- 文章处理逻辑 ---
function getPosts() {
  // ...从数据库查询文章...
  return [{ id: 1, title: '...'}];
}
function createPost(title, content) {
  // ...向数据库插入新文章...
}

// --- Web服务器逻辑 ---
const http = require('http');
// ...创建服务器，处理路由...
// if (url === '/login') { login('user', 'pass'); }
// if (url === '/posts') { getPosts(); }
// ...成百上千行代码...

connectToDatabase();
// ...
```

这个文件在只有几十行的时候看起来还行，但当它增长到几千行时，一场灾难就开始了。你会遇到**所有**这些问题：

1.  **命名冲突 (Naming Collisions)**:
    假设“文章处理”部分也需要一个`connect`函数，或者“用户认证”部分想定义一个名为`posts`的变量，这就会与已有的变量或函数名冲突，导致难以追踪的bug。

2.  **代码难以阅读和维护 (Readability & Maintainability)**:
    你想修改一个数据库相关的配置，你需要在数千行代码的“泥潭”里上下滚动，去找到那几行相关的代码。整个文件的逻辑是交织在一起的，牵一发而动全身。

3.  **无法复用 (Reusability)**:
    现在，你想在另一个项目中也使用这套“用户认证逻辑”。怎么办？只能去`server.js`里，小心翼翼地把相关的几十行代码手动复制粘贴过去。如果原来的逻辑有bug修复，你还得记得到所有复制过的地方去同步修改。

4.  **团队协作的噩梦 (Collaboration)**:
    如果小明负责用户模块，小红负责文章模块，他们俩都要修改同一个`server.js`文件。在使用Git这样的版本控制工具时，他们会频繁地遇到代码合并冲突，极大地降低了开发效率。

---

#### **2. 模块化的核心思想 — “分而治之”的智慧**

为了解决上述所有问题，天才的程序员们提出了“模块化”的思想。这个思想的核心就是中国的一句古话：**“分而治之”**。

我们不再把所有鸡蛋放在一个篮子里，而是把代码按**功能**或**职责**，拆分到不同的、独立的文件中。每一个文件，就是一个**模块 (Module)**。

模块化带来了三大革命性的好处：

* **封装 (Encapsulation)**:
  每个模块就像一个独立的“黑盒子”。比如，一个`database.js`模块，它内部可能有几十个变量和辅助函数来实现连接池、重连等复杂逻辑，但它**只对外暴露（export）一个`connect`函数**。外界（其他模块）根本不需要关心它内部的实现细节，只需要知道调用`connect`函数就能连上数据库即可。这大大降低了系统的复杂度。

* **独立作用域 (Scoping)**:
  这是解决命名冲突的法宝。**每个模块文件都有自己独立的、私有的变量作用域**。你在`user.js`里定义的变量`currentUser`，和你在`post.js`里定义的变量`currentUser`，是完全不同的两个变量，它们被隔离在各自的模块里，互不干扰。这彻底消除了全局变量污染的问题。

* **依赖管理 (Dependency Management)**:
  模块化提供了一套清晰的“声明”机制。`app.js`模块可以在代码的开头明确指出：“我的工作，需要`database.js`和`user.js`的帮助”。这种明确的依赖关系，让代码的结构一目了然。

  ```javascript
  // app.js
  const db = require('./database.js'); // 我依赖数据库模块
  const user = require('./user.js');   // 我依赖用户模块
  ```

#### **3. Node.js 的选择：CommonJS (CJS) — 为服务器而生**

当Node.js在2009年诞生时，JavaScript语言本身还没有官方的模块化标准。于是，Node.js的作者选择了社区制定的**CommonJS (简称CJS)** 规范，作为自己的模块化实现。

CommonJS规范有几个非常符合**服务器端**环境的特点：

1.  **模块是同步加载的**:
    当你写 `const fs = require('fs');` 时，Node.js会**停下当前代码的执行**，去硬盘上找到`fs`模块，把它加载进内存，执行完毕后，再回来继续执行你后面的代码。

2.  **为什么在服务器上“同步”是合理的？**
    *   **文件在本地**: 服务器运行时，它所依赖的所有模块文件（比如你写的`database.js`）都存放在同一台机器的硬盘上。从硬盘读取文件的速度是非常快的（通常是毫秒级）。
    *   **启动时加载**: 这些模块加载通常只在程序**第一次启动**时发生一次。在服务器启动阶段，花几百毫秒去同步加载所有依赖，来换取后续代码编写的简单清晰，是完全值得的。
    *   **与浏览器的对比**: 这与浏览器环境截然不同。在浏览器里，如果你要加载一个模块，可能需要发起一个网络请求去另一台服务器下载这个`.js`文件，这个过程可能耗时几秒钟。如果用同步加载，整个网页都会被“冻结”，无法响应用户操作，这是不可接受的。所以，浏览器的ES Modules规范被设计成了**异步加载**。

**小结:**

*   **模块化**是为了解决**命名冲突、可维护性、可复用性、团队协作**等一系列问题而诞生的软件工程最佳实践。
*   它的核心思想是**封装、独立作用域和明确的依赖关系**。
*   Node.js采用了**CommonJS**模块规范，这是一种**同步加载**的规范，非常适合服务器端环境。

### **模块的“契约” — `module.exports` 与 `require`**

你可以把模块化想象成一个公司里的不同部门。`module.exports`就是每个部门向外提交的“工作成果报告”，而`require`就是你去其他部门“索取报告”的动作。

---

#### **1. 导出模块：`module.exports` — 定义你的“公开接口”**

在Node.js中，你写的每一个`.js`文件，在执行前都会被Node.js用一个函数包裹起来，大致是这样的：

```javascript
(function(exports, require, module, __filename, __dirname) {
  // 你写的所有代码，实际上都在这个函数内部
  // const PI = 3.14;
  // function add(a, b) { ... }
});
```

这个函数包装解释了为什么你在每个文件里都能直接使用`require`、`module`这些变量，因为它们是作为参数传进来的！

**A. `module` 对象**

*   `module`对象代表了当前模块自身。它包含了关于当前模块的各种信息，比如它的ID、路径等。
*   你可以随时在代码里打印它看看：`console.log(module);`

**B. `module.exports` — 唯一的出口**

*   `module`对象上最重要的属性就是`exports`。
*   **初始状态**: 在你的代码开始执行前，`module.exports`被初始化为一个**空对象 `{}`**。
*   **核心规则**: 当其他文件`require`你的这个模块时，它们得到的就是你**最终赋给`module.exports`的那个值**。

**C. 如何导出？**

你可以导出任何JavaScript支持的数据类型。

*   **导出对象（最常见）**: 这是最灵活、最推荐的方式，因为它允许你一次性导出多个变量或函数。
*   **导出函数**: 当你的模块只做一件事时，可以直接导出一个函数。
*   **导出类、字符串、数字等**: 同样可行。

**【实战练习 1：创建`math.js`模块】**

1.  在你的项目里创建一个新文件 `math.js`。
2.  写入以下代码：

```javascript
// math.js

// 这两个函数是模块私有的，外界无法直接访问
const add = (a, b) => a + b;
const subtract = (a, b) => a - b;

const PI = 3.14159; // 这个常量也是私有的

// 我们决定只把 add 和 subtract 函数暴露出去
// 我们正在修改那个初始的空对象 {}
module.exports.add = add;
module.exports.subtract = subtract;

// 你也可以导出一个全新的对象，这更常见
// module.exports = {
//   add: add,
//   subtract: subtract
// };

// 甚至使用ES6的简写
// module.exports = { add, subtract };
```

现在，`math.js`这个模块的“工作成果报告”(`module.exports`)就已经准备好了，它是一个包含了`add`和`subtract`两个方法的对象。

---

#### **2. 导入模块：`require()` — 使用他人的“成果”**

`require()`是连接模块的桥梁。它去“别的部门”，拿回那份“工作成果报告”。

*   **作用**: 加载并执行一个模块，然后返回该模块的`module.exports`。
*   **同步性**: `require`是同步的。程序会在这里**暂停**，直到被依赖的模块加载完成。
*   **模块缓存 (Module Caching)**: Node.js非常聪明。当一个模块**第一次**被`require`时，Node.js会：
    1.  执行该模块的代码。
    2.  将其`module.exports`的结果**缓存**在内存中。
        当你的程序**再次**`require`同一个模块时，Node.js会**跳过第一步**，直接从缓存中返回那个已经被导出的对象。这极大地提升了性能，也确保了模块实例的唯一性。

**【实战练习 2：创建`app.js`使用`math.js`】**

1. 在与`math.js`同级的目录下，创建`app.js`。

2. 写入以下代码：

   ```js
   // app.js
   
   // 1. 使用require加载math模块。'./'表示相对路径
   // mathUtils变量现在的值，就是math.js中module.exports的那个对象
   const mathUtils = require('./math.js');
   
   // 演示模块缓存：再次require
   const mathUtilsAgain = require('./math.js');
   
   // 比较一下，看看它们是不是同一个对象
   console.log('两次require是否是同一个对象:', mathUtils === mathUtilsAgain); // -> true
   
   // 2. 使用导入的模块
   const sum = mathUtils.add(5, 3);
   const difference = mathUtils.subtract(10, 4);
   
   console.log(`5 + 3 = ${sum}`);
   console.log(`10 - 4 = ${difference}`);
   
   // 尝试访问math.js中的私有变量PI
   // console.log(mathUtils.PI); // -> undefined (因为PI没有被导出)
   ```

*   **运行 `node app.js`**: 你会看到正确的计算结果，以及`true`的输出，证明了模块缓存的存在。

#### **3. `exports` 的“陷阱” — 别跟丢了引用**

这是CommonJS里一个非常容易让人困惑的地方，但一旦理解了，就再也不会犯错。

在每个模块的开头，Node.js为了方便你，帮你多做了一件事：

```javascript
// 在你的代码执行前，可以想象有这么一行代码：
let exports = module.exports;
```

这意味着，`exports`和`module.exports`一开始指向的是**同一个空对象 `{}`**。

* **正确的用法**: 给`exports`**添加属性**。

  ```javascript
  exports.add = (a, b) => a + b;
  // 这行代码，因为exports和module.exports指向同一个对象，
  // 所以实际上修改的是那个共享的对象。
  // 效果等同于: module.exports.add = ...
  ```

* **【错误】的用法**: 直接给`exports`**赋一个新值**。

  ```javascript
  // **【 千万不要这么做! 】**
  exports = {
    add: (a, b) => a + b
  };
  ```

  当你执行 `exports = ...` 时，你并没有修改`module.exports`。你只是让`exports`这个变量，不再指向`module.exports`，而是指向了一个**你新创建的对象**。然而，Node.js的`require`系统**只认`module.exports`**。你的修改对外界来说，是完全无效的。

**一张图解释：**

*   **初始**: `[exports] -----> {} <----- [module.exports]`
*   **正确**: `exports.add = ...`
    `[exports] -----> { add: ... } <----- [module.exports]` (修改的是同一个对象)
*   **错误**: `exports = { ... }`
    `[exports] -----> { add: ... }` (指向了新对象)
    `[module.exports] -----> {}` (还指向旧的空对象)

**最佳实践:**

> 为了避免任何可能的混淆，**建议你始终只使用 `module.exports`**。要么给`module.exports`添加属性，要么直接给它赋一个新值。把`exports`这个快捷方式忘掉，可以让你省去很多麻烦。

**小结:**

*   使用 **`module.exports`** 来定义一个模块的“公开接口”，决定了什么东西可以被外界访问。
*   使用 **`require('./path/to/module')`** 来加载一个模块，它的返回值就是被加载模块的`module.exports`。
*   Node.js有**模块缓存**机制，确保模块只被执行一次。
*   `exports` 只是 `module.exports` 的一个引用别名，**永远不要直接给 `exports` 赋值**。

### ** 模块解析规则**

#### **1. 三类模块：Node.js 世界的三种“公民”**

首先，我们要认识到，Node.js 世界里存在三种不同“身份”的模块，`require` 在对待它们时，有不同的策略。

**A. 核心模块 (Core Modules) — “皇亲国戚”**

* **它们是谁？** `http`, `fs`, `path`, `os`, `events` 等。这些是Node.js官方内置的、构成其核心功能的模块。它们被编译进了Node.js的二进制可执行文件中。

* **如何引用？** 直接使用它们的官方名称。

  ```javascript
  const fs = require('fs');
  const path = require('path');
  ```

* **特点**:

  *   **无需安装**: 开箱即用。
  *   **优先级最高**: `require` 在寻路时，会第一个检查你要的是不是核心模块。
  *   **无法被覆盖**: 即使你在项目里创建一个名为 `fs.js` 的文件，`require('fs')` 仍然会加载核心模块，而不是你的文件。

**B. 文件模块 (File Modules) — “本地居民”**

* **它们是谁？** 所有由**你自己编写**的、用来组织项目代码的 `.js` 文件。比如我们之前写的 `math.js`。

* **如何引用？** 必须使用**路径**来指明它们的位置。

  * **相对路径**: 以 `./` (当前目录) 或 `../` (上级目录) 开头。这是**最常用**的方式。

    ```javascript
    const mathUtils = require('./utils/math.js');
    const config = require('../config.js');
    ```

  * **绝对路径**: 以 `/` (POSIX) 或 `C:\` (Windows) 开头。这种方式用得比较少，因为它会降低项目的可移植性。

    ```javascript
    // 很少这么用
    const logger = require('/var/log/my-app/logger.js');
    ```

* **省略 `.js` 后缀**: 通常你可以省略 `.js` 后缀，Node.js会自动帮你尝试添加。`require('./utils/math')` 和 `require('./utils/math.js')` 是等效的。

**C. 第三方模块 (Third-party Modules) — “外来专家”**

* **它们是谁？** 通过NPM (Node Package Manager) 安装的、由社区贡献的各种强大的包（package），比如 `express`, `axios`, `lodash` 等。

* **它们住在哪？** 当你执行 `npm install express` 时，`express` 这个包会被下载并存放在你项目根目录下的 `node_modules` 文件夹里。

* **如何引用？** 直接使用你在`npm install`时用的那个**包名**。

  ```javascript
  const express = require('express');
  const _ = require('lodash');
  ```

* **特点**: Node.js会有一套特殊的“向上查找”机制来定位它们。

#### **2. `require()` 的解析流程 **

现在，我们来揭晓 `require` 函数内部的完整“思考过程”。当它拿到一个模块标识符`X`时（比如 `require('fs')` 或 `require('./math')`），它会像一个侦探一样，严格按照以下步骤进行调查：

**`require('X')` 流程图：**

1.  **第一站：检查“皇家族谱”（核心模块缓存）**
    *   `require` 会问：“`X`是我认识的核心模块之一吗？”
    *   **如果是** (`X` 是 `fs`, `http` 等)，就直接从内存中加载，寻路结束。
    *   **如果不是**，进入下一步。

2.  **第二站：检查“地址格式”（判断是否为路径）**
    *   `require` 会问：“`X`是不是以 `./`, `../`, 或 `/` 开头的？”
    *   **如果是**，`require` 就把它当做**文件模块**，并按照给定的路径去寻找文件。
        *   它会先尝试直接找 `X` 这个文件。
        *   如果找不到，它会尝试 `X.js`。
        *   如果还找不到，它会尝试 `X.json`。
        *   如果还找不到，它会尝试把 `X` 当做一个目录，然后寻找 `X/index.js`。
        *   如果都找不到，就抛出 `MODULE_NOT_FOUND` 错误。
    *   **如果不是**路径格式，进入下一步。

3.  **第三站：搜查“本地社区”及“上级社区”（`node_modules` 爬升）**
    *   现在 `require` 确定 `X` 既不是核心模块，也不是一个文件路径，那么它就断定这是一个**第三方模块**。
    *   它的搜查行动开始：
        1.  **从当前文件所在的目录开始**，寻找该目录下是否存在一个 `node_modules` 文件夹。
        2.  **如果在**，就在 `node_modules` 里寻找一个名为 `X` 的文件夹（比如 `node_modules/express`）。
        3.  **如果找到了**，就加载 `X` 文件夹里 `package.json` 文件中 `main` 字段指定的文件（通常是 `index.js`），寻路结束。
        4.  **如果在当前目录的 `node_modules` 里没找到，或者当前目录根本没有 `node_modules`**，侦探就会**“向上走一步”**，进入**父级目录**。
        5.  在父级目录里，**重复步骤 1-4**。
        6.  这个“向上爬升”的过程会一直持续，直到系统的**根目录** (`/`) 为止。
        7.  如果爬到了根目录还是没找到，就最终抛出 `MODULE_NOT_FOUND` 错误。

**【一个生动的例子】**

假设你的文件 `/Users/jane/project/src/app.js` 里写了 `require('lodash')`。

`require` 的寻路之旅：

1.  不是核心模块。
2.  不是路径。
3.  开始第三方模块查找：
    *   在 `/Users/jane/project/src/node_modules/lodash` 找... 没找到。
    *   向上走，在 `/Users/jane/project/node_modules/lodash` 找... 找到了！加载它。寻路结束。

**小结:**

*   Node.js有**核心模块**、**文件模块**和**第三方模块**三大家族。
*   `require`的解析规则是一个有**明确优先级**的算法：**核心模块 > 文件路径 > `node_modules`爬升**。
*   这个`node_modules`的向上爬升机制，是Node.js依赖管理的核心，它允许你在项目的任何一个子目录里，都能`require`到安装在项目根目录的包。

---

到目前为止，我们深入学习的都是Node.js的“传统母语”——CommonJS (`require`/`module.exports`)。但是，自从ES6 (ES2015) 发布以来，JavaScript语言本身拥有了**官方的、统一的模块化标准**——**ES Modules (简称ESM)**。

你在前端框架（如Vue, React）中使用的 `import` 和 `export` 语法，就是ESM。

Node.js作为一个与时俱进的平台，也已经全面支持了ESM。这节课的目标是让你了解如何在Node.js环境中使用ESM，并清楚地知道它和我们已经学过的CommonJS有什么核心区别。
